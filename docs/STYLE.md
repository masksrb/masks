# Writing the masks docs

The docs follow the Ruby on Rails
[API documentation guidelines](https://guides.rubyonrails.org/api_documentation_guidelines.html)
and [guides guidelines](https://guides.rubyonrails.org/ruby_on_rails_guides_guidelines.html).

## Structure

| | |
| --- | --- |
| Use masks | Pages under `use/`, for the person who runs masks and the people who sign in through it. Each page says what to do in steps, names the words on the screen in bold, and shows no environment variable, scope, or URL path unless the reader has to type it. |
| Build with masks | Pages under `build/`, for developers and operators, grouped by what the reader is doing: running masks, signing people in, connecting apps, and sending events. One subject per page, written by hand. `core-concepts` explains how masks works; the rest say how to use a part of it. Quickstart and Demo are a path that works end to end on a fresh `./dev` stack. |
| Reference | `manage`, `javascript/client`, `ruby/client`, and `ruby/rails` are generated by `./dev reference`. Never edit them by hand. `specs`, `environment`, and `style-guide` are written by hand, and `./dev reference` checks `environment` against every variable the code reads. |

## Voice and tone

- Keep one voice everywhere: trustworthy, confident, empowering, practical, and clear.
- Fit the tone to the reader's situation. Be direct and serious in errors and warnings. Be helpful
  and encouraging in setup and onboarding.
- Never be playful in an error. Write "Upload failed. Use a PNG or JPG file."

## Plain language

- Aim for a grade 7 reading level. Use everyday words, and explain a technical term the first time
  a page uses it.
- Leave out idioms and irony. They get misread and mistranslated.
- Choose clarity over brevity. A short line that can be misread is worse than a longer one that
  cannot.
- Make each page easy to scan with headings, lists, and short sentences. Split a long paragraph
  into a one-line summary and a list.
- Say each thing once. Do not repeat a heading in the text below it, or show the same content two
  ways.
- Put the most important information and tasks first.
- Break a task into numbered steps, with one action in each step.
- Start a call to action with a strong verb: "Create template".
- Guide the reader. Give them what they need to decide for themselves.
- Spell out words instead of symbols and abbreviations.

## Wording

- Write simple, declarative sentences. Get to the point.
- Use the present tense: "Returns the feed", not "Will return the feed".
- Use American English and the Oxford comma: "color", "authorize", "red, white,
  and blue".
- Pages may address the reader as "you".
- Say what the software does. It does not decide, know, want, or remember.
- Use one exact word for each thing, action, or concept, from [Words](#words) below. Name things
  by the names in the code and the UI. Put UI labels in bold and
  code, paths, variables, and commands in backticks.
- Document edge cases: a tenant with no clients, an expired token, a key that
  has been rotated.

## Plain prose, no flourishes

These patterns read as generated text. Leave them out.

- Contrast framing: "X, not Y", "rather than", "isn't X, it's Y".
- Closing aphorisms: a last sentence that sums up with a twist.
- Fragments for rhythm: "One index, lexical and semantic, fused."
- Lists of three for effect, and colons that set up a reveal.
- Em dashes as general punctuation. Use a period, a comma, or parentheses.
- Metaphor and poetic nouns: "the shape of it", "a pass over", "carries",
  "signature", "the one record", "rose window" outside the design page.
- Filler and hype: simply, just, easily, seamless, powerful, robust, leverage,
  crucial, ensure, under the hood.
- Rhetorical questions.

If a sentence would survive in a Rails guide, it belongs here.

## Formatting

- Headings are `##` for sections and `###` for subsections, in sentence case.
- Links describe their target: "see [custom domains](/build/self-hosting/#custom-domains)",
  never "see here" or "more".
- Shell examples are fenced as `sh` and show only the command.
- Asides are `:::note`, `:::tip`, or `:::caution`, used sparingly. A caution
  is for something that loses data or weakens security.
- Two-column tables with an empty header serve as definition lists.

## Words

Every screen uses one name for each thing. The words live in `engine/config/locales/en/` and
`server/app/frontend/manage/`.

A few words change with the reader:

- **Managers** read `/manage`.
- **People** read the sign-in pages, their account page, and the email masks sends.

| **connected account** | connection, linked account | an account elsewhere linked through a provider |

screen says *account*.

### Verbs and nouns

**Sign in**, **sign out**, and **sign up** are verbs. **Sign-in**, **sign-out**, and **signup** are
nouns. A button says *Sign in*, a chart counts *sign-ins*, and a policy decides whether *signup* is
open.

### Events

Each event's label is written once, in `events.yml`. `/manage` gets it as `label` on `Event` and
`EventAction`, and the account page reads the same file.

- A label is a noun and then a verb in the past tense: *Passkey added*, *Client archived*, or
  *Device sign-in refused*.
- A change is always *changed*. No label says *edited* or *updated*.

### Buttons and empty lists

A page's add button names what it adds: *Add actor*, *Add policy*, *Add provider*, *Add a service*.
The form's own submit is *Add* or *Save*.

An empty list says *Nothing yet.* If nothing will ever show up in it on its own, it says *None.*

A link to the rest of a list names the list, such as *All activity*.
