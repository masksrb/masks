---
title: Device sign-in
description: Signing in something with no browser of its own.
---

A television, a CLI, a box on a shelf — anything that can show a short code but cannot hold a
browser signs in through the device grant, [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628).
The device asks for a code, shows it, and waits. The person walks over to a phone and types it in.

The client has to be registered for the grant, the same way it is registered for any other:

```json
{ "grant_types": ["urn:ietf:params:oauth:grant-type:device_code"] }
```

## What the device does

```sh
curl -X POST https://acme.auth.example.com/device_authorization \
  -d client_id=... -d scope="openid profile"
```

```json
{
  "device_code": "...",
  "user_code": "BCDF-GHJK",
  "verification_uri": "https://acme.auth.example.com/device",
  "verification_uri_complete": "https://acme.auth.example.com/device?user_code=BCDF-GHJK",
  "expires_in": 900,
  "interval": 5
}
```

Show the `user_code` and the `verification_uri`. If the device can draw a QR code, point it at
`verification_uri_complete` so the person does not have to type anything.

Then poll the token endpoint, no faster than `interval` seconds:

```sh
curl -X POST https://acme.auth.example.com/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:device_code \
  -d device_code=... -d client_id=...
```

| answer | what it means |
| --- | --- |
| `authorization_pending` | nobody has typed the code in yet — keep waiting |
| `slow_down` | you polled inside `interval` — add five seconds and carry on |
| `access_denied` | the person said no. Stop. |
| `expired_token` | fifteen minutes went by. Ask for a new code. |
| a token | done |

A device code is good for exactly one token. Polling again after it worked is an `invalid_grant`,
which is what turns a stolen code into a dead one.

## What the person does

They open `/device`, type the code, and sign in the way they always do — password, passkey,
a provider, a second factor, whatever the tenant asks of them. Then they see the same consent
screen an application gets, naming the device's client and the scopes it asked for. Approving
hands the waiting device its token; declining leaves the device with `access_denied`.

The code is eight letters from a twenty-letter alphabet with no vowels in it, so it cannot spell
anything and cannot be misread between `O` and `0`. Case and dashes are ignored — `bcdfghjk` is
the same code as `BCDF-GHJK`. Attempts against `/device` are rate limited per address, because a
short code is only safe while guessing it is slow.
