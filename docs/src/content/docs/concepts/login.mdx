title: The login machine
description: Eleven ordered states — the order is the flow, and adding a factor is adding two files.
---

Sign-in is an ordered list of states. Each one reloads, handles the event, then insists. The first
to insist names the prompt you see.

`server/app/models/login.rb`, `server/app/logins/`

```ruby
class Login
  STATES = [
    LoginStates::Setup,
    LoginStates::Invitation,
    LoginStates::PasswordReset,
    LoginStates::Passkey,
    LoginStates::Identifier,
    LoginStates::Password,
    LoginStates::FirstFactor,
    LoginStates::OneTimePassword,
    LoginStates::BackupCode,
    LoginStates::SecondFactor,
    LoginStates::Consent
  ].freeze
end
```

The order of `STATES` is the flow. There is no state diagram, no `next_step` column and no
controller deciding what comes after what.

| State | Ahead of `Identifier` because |
| --- | --- |
| `Setup` | a tenant with no actors has nobody to identify |
| `Invitation` | the browser is carrying a claim on a specific account |
| `PasswordReset` | so is a reset link |
| `Passkey` | a discoverable credential already knows whose it is |

`Setup` runs once per tenant and creates the owner. `Invitation` turns an account with no password
into one that has one. `PasswordReset` handles both the `forgot-password` event and the reset link,
and ends at `factored! :first_factor` only, so a reset is never a way past a second factor.

## How a pass runs

```ruby
def update
  states.each(&:reload!)
  states.each { |state| state.event!(event) } if event
  states.each(&:factor!)

  @prompt = SETTLED
rescue LoginState::PromptRequired => denial
  @prompt = denial.prompt
rescue LoginState::Refused => denial
  @refusal = denial
ensure
  states.each(&:cleanup!)
end
```

A state insists by raising `PromptRequired`, so the first unsatisfied state in declaration order
wins and the rest never run. `Refused` ends the flow with an OAuth error instead; `Consent` raises
it on `decline`.

The client gets the prompt name and renders one component for it:

```json
{ "prompt": "first-factor", "settled": false, "warnings": ["invalid-credentials"],
  "identifier": "owner", "actor": { "nickname": "owner", "name": "Ada" } }
```

`Login#as_json` merges each enabled state's own `as_json`, so a prompt arrives with what it needs.
`Passkey` adds its WebAuthn options; `Consent` adds the scopes and audience being asked for.

## A state declares three things

```ruby
module LoginStates
  class Password < LoginState
    EXPIRY = 12.hours

    accepts :password

    handles "password" do
      verify
    end

    def verify
      return warn!("missing-identifier") if login.identifier.blank?

      if (authenticated = Actor.authenticate(login.identifier, update(:password)))
        login.actor = authenticated
        factored! :first_factor, expiry: EXPIRY
        login.noted! "pwd"
      else
        warn! "invalid-credentials"
      end
    end
  end
end
```

| | |
| --- | --- |
| `accepts` | the parameters this state may read, and the only ones it can |
| `handles` | an event name from the client, and what to do with it |
| `prompts` | a prompt name, and the condition under which it must be shown |

All three inherit through `inherited_from`, so a subclass gets its parent's and can add.
`Login.permitted_updates` is the union of every state's `accepts` — the strong parameters of the
login endpoint.

`enabled?` gates a state entirely:

| | |
| --- | --- |
| `Setup` | a tenant with no actors |
| `Invitation` | an invitation is present |
| `Passkey` | `::Passkey.exists?` |
| `OneTimePassword` / `SecondFactor` | `actor&.otp?` |
| `BackupCode` | `actor&.backup_codes?` |
| `Consent` | `request.present?` |

## Verifying and insisting

`Password` has no `prompts` block, and `FirstFactor` has nothing else:

```ruby
class FirstFactor < LoginState
  prompts "first-factor" do
    !touched?(:first_factor)
  end
end
```

One state knows how to check a password; a different one knows the flow cannot continue until some
first factor has been satisfied. `OneTimePassword` / `BackupCode` and `SecondFactor` are the same
pair a step later. A second way of proving a first factor can be added without touching what
insists on one.

## What proves what

| State | Sets | Expiry | `amr` |
| --- | --- | --- | --- |
| `Password` | `first_factor` | 12h | `pwd` |
| `Passkey` | `first_factor` | 12h | `swk` |
| `Passkey`, user-verified | *and* `second_factor` | 12h | `user`, `mfa` |
| `OneTimePassword` | `second_factor` | 12h | `otp`, `mfa` |
| `BackupCode` | `second_factor` | 12h | `otp`, `mfa` |
| `Setup` / `Invitation` / `PasswordReset` | `first_factor` | 12h | — |
| `Consent` | `consent` | 1h | — |

One passkey can be both factors. It ends at `first_factor`, and additionally at `second_factor` when
the assertion reports the authenticator verified the person. A passkey reporting no user
verification stops at the first factor.

`amr` describes the sign-in rather than the account. See [Tokens](/concepts/tokens).

## Factors expire

`factored!(key, expiry:)` records `at` and `until`. `touched?` is false once `until` passes.

```ruby
factored! :first_factor, expiry: 12.hours
```

So a second factor left pending for half a day does not leave a half-authenticated session lying
around. `start_over!` on a state expires only what it owns.

`Login#reauthenticating?` and `#stale?` make `first_factored?` and `second_factored?` false again
when the request asked for `prompt=login` or set a `max_age` the sign-in no longer satisfies.

## Adding a factor

A `LoginState` in `server/app/logins/login_states/`, and a prompt component. Its position in
`Login::STATES` decides when it runs.

Prompts exist twice, as an ERB partial and a Svelte component, because sign-in works without
JavaScript (`server/test/integration/no_javascript_test.rb`). Both post the same events to the same
endpoint, and `LoginsController#update` answers HTML or JSON from one code path.

:::note[The identifier step never looks you up]
`Identifier` stores what you typed and validates nothing about whether it exists. Looking the actor
up there would make the first step of sign-in a user-enumeration oracle — the property
[hardening](/concepts/hardening) measures.
:::
