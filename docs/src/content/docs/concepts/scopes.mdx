---
title: Scopes
description: What a token is allowed to do, and the prefixes an app publishes beneath.
---

A scope is a string. Five are standard — `openid`, `profile`, `email`, `offline_access` and
`identities`, which names the [accounts elsewhere](/concepts/providers/#calling-a-providers-api)
somebody signs in with — and masks reserves the `masks:` prefix for itself.

| Scope | |
| --- | --- |
| `masks:manage` | the console, and the GraphQL API behind it |
| `masks:handshake` | connect an application to this tenant |
| `masks:scim` | provision people over SCIM, for a client that signs in as itself — see [provisioning](/concepts/provisioning/) |
| `masks:delegate:<provider>` | use somebody's account at that provider while they are away — see [delegation](/concepts/delegation/) |

Only an approved client may hold a `masks:` scope. `masks:delegate:` scopes are the exception on the
actor's side: every person holds them for their own accounts, and consents to each application
separately.

## Prefixes

A scope ending in a colon is a prefix — a [namespace](/concepts/namespaces/) an application claims,
so it can publish scopes of its own beneath it without masks knowing them in advance.

Coverage is one-directional: holding `things:` grants `things:read`, but a bare prefix is never
itself *covered* by anything. So a prefix cannot be granted by holding it — it is granted by
claiming the namespace, which adds it to the actor's list outright.

## The ceiling

Every grant is bounded twice: by the client's `allowed_scopes`, and by the actor's own list. A token
carries the intersection, never more, and an actor stripped of a scope cannot keep using a token
that still names it.
