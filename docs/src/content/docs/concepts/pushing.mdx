---
title: Pushed requests
description: Handing an authorization request to the server before sending anybody to it.
---

An ordinary authorization request travels in the browser's address bar. Every parameter — the
scopes, the resources, the redirect URI, the PKCE challenge — is visible to the person, to anything
reading their history or logs, and to whatever else the page later loads.

A pushed request moves that to the back channel. The client posts the request to `/par` over the
same authenticated connection it uses for `/token`, and gets back a reference to it. Only the
reference goes in the URL.

masks implements [RFC 9126](https://www.rfc-editor.org/rfc/rfc9126.html). The endpoint is
advertised as `pushed_authorization_request_endpoint`.

## Pushing one

Post the parameters you would otherwise have put in the query, authenticating the way you would at
the token endpoint. `client_id` is one of those parameters, so it belongs in the body even when the
same id is already in the credentials you authenticate with.

```sh
curl -u "$CLIENT_ID:$CLIENT_SECRET" https://demo.auth.example.com/par \
  -d client_id="$CLIENT_ID" \
  -d response_type=code \
  -d redirect_uri=https://app.example.com/cb \
  -d scope="openid profile" \
  -d code_challenge="$CHALLENGE" \
  -d code_challenge_method=S256 \
  -d state="$STATE"
```

```json
{
  "request_uri": "urn:ietf:params:oauth:request_uri:8mZ1...",
  "expires_in": 90
}
```

Then send the person to `/authorize` with nothing but the client and that reference:

```
https://demo.auth.example.com/authorize
  ?client_id=...
  &request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3A8mZ1...
```

A public client — `token_endpoint_auth_method` of `none` — pushes with its `client_id` and no
secret, and still gets the benefit: the request itself never reaches the address bar.

## What the reference is worth

| | |
| --- | --- |
| lifetime | 90 seconds |
| uses | one |
| bound to | the client that pushed it |

It is spent when it is followed, whether or not the `client_id` beside it was right — a reference
that has been in an address bar has had its chance. Following one twice, following one that has
expired, or following one pushed by a different client all answer `invalid_request_uri`.

Anything else in the query is ignored. The request is what was pushed, so appending a wider `scope`
or a different `redirect_uri` on the way to `/authorize` changes nothing.

## Requiring it

A client can be held to it, from the console or through the manage API:

```graphql
mutation {
  updateClient(clientId: "...", requirePushedAuthorizationRequests: true) {
    client { clientId }
  }
}
```

Once required, a plain `/authorize` link for that client is refused with `invalid_request`. Turn it
on after the client is pushing, not before. A self-registering client can ask for it at
registration with the same name.

Signing in and consenting return through a URL this server builds for itself, and that return is
the same request rather than a second one — requiring a push does not break the flow it started.

## Signing it

Pushing keeps the request off the front channel. Signing it proves the client wrote it. A client
that has registered `jwks` or a `jwks_uri` may send the whole request as a request object
([RFC 9101](https://www.rfc-editor.org/rfc/rfc9101.html)): a JWT it signs with one of those keys,
carrying the parameters as claims.

```json
{
  "iss": "$CLIENT_ID",
  "aud": "https://demo.auth.example.com",
  "client_id": "$CLIENT_ID",
  "exp": 1789000300,
  "nbf": 1789000000,
  "jti": "5c1f...",
  "response_type": "code",
  "redirect_uri": "https://app.example.com/cb",
  "scope": "openid profile",
  "code_challenge": "$CHALLENGE",
  "code_challenge_method": "S256",
  "state": "$STATE"
}
```

Send it as `request`, beside the `client_id`, either straight to `/authorize` or pushed to `/par`,
where the `client_id` comes from how the client authenticated. Typing it `oauth-authz-req+jwt` is
recommended.

| | |
| --- | --- |
| signed with | RSA, RSA-PSS or ECDSA, by a key the client registered — never `none`, never a shared secret |
| `iss` | the client |
| `aud` | this issuer |
| `client_id` | the same client as the one beside it |
| `exp` | required, and within the hour |
| `nbf` | if present, not in the future and not more than an hour gone |
| `jti` | if present, spent the first time it is used |

When a request object arrives, it is the entire request. Nothing in the query beside it is read,
so an unsigned `scope` or `redirect_uri` added on the way is ignored rather than merged. One that
does not verify is refused with `invalid_request_object`, including one that carries a `request`
or `request_uri` of its own.

`requireSignedRequestObject` holds a client to signing, the way `requirePushedAuthorizationRequests`
holds it to pushing. Holding a client to both is what FAPI 2.0 asks for. Discovery answers
`request_parameter_supported: true` and lists the algorithms in
`request_object_signing_alg_values_supported`.

A `request_uri` is only ever one this server issued from `/par`. masks never fetches a request
object from a URL a client names, so `request_uri_parameter_supported` stays `false`.
