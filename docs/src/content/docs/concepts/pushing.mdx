---
title: Pushed requests
description: How a client sends its authorization request to masks directly before redirecting the person.
---

An ordinary authorization request is sent in the browser's address bar. Every parameter, including
the scopes, the resources, the redirect URI, and the PKCE challenge, is visible to the person, to
anything that reads their history or logs, and to any page that loads afterward.

A pushed request sends those parameters over the back channel instead. The client posts the request
to `/par` with the same client authentication it uses at `/token`, and receives a reference to the
request. Only the reference is sent in the URL.

masks implements [RFC 9126](https://www.rfc-editor.org/rfc/rfc9126.html). Discovery advertises the
endpoint as `pushed_authorization_request_endpoint`.

## Pushing a request

1. The client posts the parameters it would otherwise put in the query string, and authenticates
   as it does at the token endpoint. `client_id` is one of those parameters, so it belongs in the
   body even when the credentials already contain the same ID.

   ```sh
   curl -u "$CLIENT_ID:$CLIENT_SECRET" https://demo.auth.example.com/par \
     -d client_id="$CLIENT_ID" \
     -d response_type=code \
     -d redirect_uri=https://app.example.com/cb \
     -d scope="openid profile" \
     -d code_challenge="$CHALLENGE" \
     -d code_challenge_method=S256 \
     -d state="$STATE"
   ```

   ```json
   {
     "request_uri": "urn:ietf:params:oauth:request_uri:8mZ1...",
     "expires_in": 90
   }
   ```

2. The client redirects the person to `/authorize` with only the client ID and the reference:

   ```
   https://demo.auth.example.com/authorize
     ?client_id=...
     &request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3A8mZ1...
   ```

A public client, whose `token_endpoint_auth_method` is `none`, pushes with its `client_id` and no
secret. Its request parameters still stay out of the address bar.

## The reference

| | |
| --- | --- |
| lifetime | 90 seconds |
| uses | one |
| bound to | the client that pushed it |

The reference is spent the first time the client that pushed it follows it to `/authorize`.
Following it a second time, following it after it expires, or presenting it with a different
client's `client_id` returns `invalid_request_uri`. A reference presented with the wrong
`client_id` is refused and is not spent.

masks ignores every other parameter in the query. The request is the one that was pushed, so a
wider `scope` or a different `redirect_uri` appended to the `/authorize` URL has no effect.

## Requiring pushed requests

A client can be required to push its requests, from the console or through the manage API:

```graphql
mutation {
  updateClient(clientId: "...", requirePushedAuthorizationRequests: true) {
    client { clientId }
  }
}
```

After this is set, masks refuses a plain `/authorize` link for that client with `invalid_request`.
Set it only after the client is already pushing its requests. A client that registers itself can
request the same setting at registration, under the same name.

When the person signs in and consents, masks returns them to a URL that it builds itself. That
return continues the same pushed request, so requiring pushed requests does not interrupt sign-in
or consent.

## Signing a request

Pushing keeps the request out of the browser. Signing the request proves that the client created
it. A client that has registered `jwks` or a `jwks_uri` may send the whole request as a request
object ([RFC 9101](https://www.rfc-editor.org/rfc/rfc9101.html)). A request object is a JWT that the
client signs with one of those keys, with the parameters as claims.

```json
{
  "iss": "$CLIENT_ID",
  "aud": "https://demo.auth.example.com",
  "client_id": "$CLIENT_ID",
  "exp": 1789000300,
  "nbf": 1789000000,
  "jti": "5c1f...",
  "response_type": "code",
  "redirect_uri": "https://app.example.com/cb",
  "scope": "openid profile",
  "code_challenge": "$CHALLENGE",
  "code_challenge_method": "S256",
  "state": "$STATE"
}
```

The client sends it as the `request` parameter, beside the `client_id`, either directly to
`/authorize` or pushed to `/par`. At `/par`, the `client_id` comes from the client's
authentication. The JWT should be typed `oauth-authz-req+jwt`.

| | |
| --- | --- |
| signed with | RSA, RSA-PSS, or ECDSA, by a key the client registered; `none` and shared secrets are refused |
| `iss` | the client |
| `aud` | this issuer |
| `client_id` | the same client as the `client_id` beside it |
| `exp` | required, and no more than an hour away |
| `nbf` | if present, not in the future and not more than an hour ago |
| `jti` | if present, spent the first time it is used |

A request object is the entire request. masks reads nothing else in the query beside it, so an
unsigned `scope` or `redirect_uri` added to the URL is ignored and is not merged in. A request
object that does not verify is refused with `invalid_request_object`. So is a request object that
contains its own `request` or `request_uri`.

`requireSignedRequestObject` requires a client to sign its requests, in the same way that
`requirePushedAuthorizationRequests` requires it to push them. FAPI 2.0 requires both. Discovery
returns `request_parameter_supported: true` and lists the accepted algorithms in
`request_object_signing_alg_values_supported`.

masks accepts only a `request_uri` that it issued from `/par`. It never fetches a request object
from a URL that a client provides, so `request_uri_parameter_supported` is `false`.
