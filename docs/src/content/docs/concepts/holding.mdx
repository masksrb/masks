---
title: Holding a token
description: How DPoP binds a token to a client's key, so a stolen token cannot be used without the key.
---

Anyone who holds a bearer token can use it. DPoP,
[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449), binds a token to a key that the client
generates and never sends. A token copied from network traffic, a log, or a browser cannot be used
without that key.

masks issues a bound token to any client that requests one, and a bearer token to any client that
does not. No configuration is required.

## Requesting a bound token

1. The client generates a key pair and keeps it.
2. For each request, the client signs a JWT called a *proof*. The proof is typed `dpop+jwt`, names
   the HTTP method and URL of the request, and includes the public key in its header.
3. The client sends the proof in the `DPoP` header of the token request:

   ```
   POST /token HTTP/1.1
   DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2Iiwiandr...
   ```

4. masks returns a bound token:

   ```json
   { "access_token": "...", "token_type": "DPoP", "expires_in": 3600 }
   ```

The token has a `cnf` claim containing `jkt`, the SHA-256 thumbprint of the public key
([RFC 7638](https://www.rfc-editor.org/rfc/rfc7638)). A resource server compares the token with the
proof sent alongside it, and refuses the request if the thumbprints differ.

The client presents the token with the `DPoP` scheme instead of `Bearer`, and with a new proof on
every request. A proof sent with a token also includes `ath`, the hash of the token, so a proof
from one request cannot be reused with a different token.

```
GET /userinfo HTTP/1.1
Authorization: DPoP eyJhbGciOiJSUzI1NiIs...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs...
```

## What masks refuses

| | |
| --- | --- |
| a bound token presented as `Bearer` | a bound token can only be used with a proof |
| a proof signed by a different key than the token is bound to | |
| a proof whose `htm` or `htu` names another request | |
| a proof with no `ath`, or the wrong one, when a token is sent with it | |
| a proof made more than 90 seconds ago, or more than 30 seconds in the future | a 60-second window plus 30 seconds of clock leeway |
| a proof whose `jti` has been seen before | a replay, detected for as long as the proof is valid |
| a proof carrying a private key, a symmetric key, or `alg: none` | |
| a proof signed with anything but `ES256`, `ES384`, `ES512`, `PS256`, `PS384`, `PS512`, or `RS256` | |

At a resource endpoint, a refused proof returns `401` with
`WWW-Authenticate: DPoP error="invalid_dpop_proof"` and an `algs` parameter that lists the
algorithms masks accepts, so the client can correct its proof. At `/token`, a refused proof returns
`400` with the error `invalid_dpop_proof` in the JSON body.

masks does not require a server-provided nonce. It records each proof's `jti` for as long as the
proof is valid and refuses a second use. A nonce would add protection only against a client that
pre-computes proofs for later use.

## Binding earlier

The binding can extend beyond a single token in two ways.

`dpop_jkt` on the authorization request binds the authorization code to the key, so a code
intercepted in the redirect cannot be redeemed by the party that intercepted it:

```
GET /authorize?...&dpop_jkt=NzbLsXh8uDCcd-6MNwXF4W_7noWXFZAfHkxZsRGC9Xs
```

A refresh token issued for a bound grant is also bound. Every refresh requires a proof from the
same key. A proof that does not match is refused *before* the refresh token is spent, so someone
without the key cannot use up another client's refresh token by guessing.

## Requiring a bound token

A client registered with `dpop_bound_access_tokens: true` is refused a token unless it sends a
proof, so it cannot be issued a bearer token.

```json
{ "client_name": "...", "dpop_bound_access_tokens": true }
```
