---
title: Tenants
description: One masks deployment serves many tenants and isolates them from each other at three layers.
---

A tenant is a subdomain with its own actors, clients, and signing keys. One deployment serves many
tenants, and no record belongs to more than one of them.

masks isolates tenants at three layers. Each layer fails in a different way:

| Layer | What it does | How it fails |
| --- | --- | --- |
| `TenantScoped` | Scopes every query in the application. | By omission. A forgotten scope leaks rows. |
| Row-level security | Applies `FORCE ROW LEVEL SECURITY` in Postgres. | It does not fail silently. See below. |
| Per-tenant signing keys | A token from one tenant has a `kid` that no other tenant can look up. | Verification refuses the token. |

The application connects to Postgres as a non-superuser role so that the table's owner cannot bypass
the second layer. A role that holds `SUPERUSER` or `BYPASSRLS` ignores every policy, and Postgres
reports nothing when it does. For this reason `Tenant.switch` queries the database once per process
for the role it is connected as, and raises instead of entering a tenant if that role holds either
privilege. Set `POSTGRES_USER` to an ordinary role.

## Entering a tenant

Application code does not enter a tenant by hand:

1. A Rack middleware resolves the request's hostname to a tenant and enters it before any
   controller runs. A hostname that resolves to no tenant receives a 404.
2. A module included in `ActiveJob::Base` records the tenant a job was enqueued in, and the worker
   enters that tenant before it performs the job.

Both apply automatically. A controller that inherits from an unexpected base class, or a job
defined by a framework, runs inside the tenant as well.

A job enqueued outside any tenant raises an error. Without that check it would perform against
whichever tenant its worker thread entered last. A job that performs maintenance across every
tenant declares it:

```ruby
class CleanupJob < ApplicationJob
  across_tenants!
end
```

Code that deliberately works across tenants uses `Tenant.switch(tenant) { ... }`. Examples are the
cleanup job above and an issuer that reads another tenant's keys. `Tenant.switch` sets a
session-scoped Postgres setting. It holds no transaction open, and the setting applies to every
query and every transaction inside the block. Outside a tenant, every query returns zero rows,
including a query through `Model.unscoped`.

Tenants are declared at deploy time. `MASKS_TENANTS` lists the subdomains to create, and
`MASKS_TENANT` serves a single tenant at every hostname. Setting both is an error. When neither is
set and no tenant exists yet, the first request creates a tenant named after the first label of its
hostname.

## Tenant settings

A tenant holds its own name, [what names an account](/concepts/actors/), whether an app may
[register itself](/concepts/clients/), which user agents may sign in, and which sign-in policy the
console uses by default. The first-run screen asks for the name. The console edits all of these
settings, and a change takes effect without a restart. When the deployment pins a setting, the
manage API refuses to write it.

| Held by the tenant | Pinned at deploy | When both are set |
| --- | --- | --- |
| `named_by` | `MASKS_NAMED_BY` | The deployment's value applies. |
| `dynamic_registration` | `MASKS_DYNAMIC_REGISTRATION` | The deployment's value applies. |
| `dynamic_client_scopes` | `MASKS_DYNAMIC_CLIENT_SCOPES` | The tenant's value applies. |
| `browsers_only` | `MASKS_BROWSERS_ONLY` | The deployment's value applies. |
| `blocked_agents` | `MASKS_BLOCKED_AGENTS` | The deployment's value applies. |
| Primary mail adapter | `MASKS_MAIL_FROM`, `MASKS_SMTP_*` | The tenant's adapter applies. |

Mail settings include a secret. A tenant sends mail through its primary mail adapter, which stores
its password encrypted in the same way the tenant stores its pairwise salt. The manage API accepts
the password but never returns it. A tenant with no mail adapter sends mail through the SMTP server
the deployment configures. If the deployment configures no mailer either, invitations and password
resets are links that a manager sends to the person by hand.
