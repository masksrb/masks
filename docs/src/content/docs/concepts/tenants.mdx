---
title: Tenants
description: One masks deployment serves many tenants, isolated three ways.
---

A tenant is a subdomain with its own actors, clients and signing keys. One deployment serves many,
and nothing crosses between them.

Isolation is three layers, because each fails differently:

| Layer | What it does | How it fails |
| --- | --- | --- |
| `TenantScoped` | scopes every query in the application | by omission — a forgotten scope leaks |
| Row-level security | `FORCE ROW LEVEL SECURITY` in Postgres | it cannot fail quietly — see below |
| Per-tenant signing keys | a token from one tenant has no `kid` the next can look up | loudly — verification refuses |

The application connects as a non-superuser role precisely so the second layer cannot be bypassed by
the table's owner. A role holding `SUPERUSER` or `BYPASSRLS` sees straight through every policy, and
Postgres says nothing when it does, so `Tenant.switch` asks the database once per process who it is
connected as and refuses to enter a tenant at all if the answer is such a role. Point
`POSTGRES_USER` at an ordinary role.

## Entering one

Nothing in the application enters a tenant by hand. A Rack middleware resolves the request's
hostname and enters it before any controller runs, and a module on `ActiveJob::Base` carries the
tenant a job was enqueued in through to the worker that performs it. Neither is opted into, so
neither can be forgotten by a controller that inherits from somewhere unexpected or a job that
belongs to a framework.

A job enqueued outside any tenant is refused rather than left to perform against whichever tenant
its worker thread happened to hold last. Maintenance meant to span every tenant says so:

```ruby
class CleanupJob < ApplicationJob
  across_tenants!
end
```

`Tenant.switch(tenant) { ... }` remains for code that deliberately crosses — the sweep above, or an
issuer reading another tenant's keys. It sets a session-scoped Postgres setting rather than a
transaction-scoped one, so it holds no transaction open and applies to every query and every
transaction beneath it. Outside a tenant a query returns nothing rather than everything:
`Model.unscoped` is zero rows, not all rows.

Tenants come from `MASKS_TENANTS` at deploy, or the first visit claims one when none are declared.

## What a tenant decides for itself

A tenant holds its own name, [what names an account](/concepts/actors/), whether an app may
[register itself](/concepts/clients/), and where its mail goes. The first-run screen asks for the
name; the console holds all four, and changing any of them restarts nothing. A
setting the deployment pins cannot be written from the console — it is refused rather than quietly
overridden.

| Held by the tenant | Pinned at deploy | When both |
| --- | --- | --- |
| `named_by` | `MASKS_NAMED_BY` | the deployment wins |
| `dynamic_registration` | `MASKS_DYNAMIC_REGISTRATION` | the deployment wins |
| `dynamic_client_scopes` | `MASKS_DYNAMIC_CLIENT_SCOPES` | the tenant wins |
| `mail_from`, `smtp_*` | `MASKS_MAIL_FROM`, `MASKS_SMTP_*` | the tenant wins |

Mail is the one that carries a secret. A tenant that names its own server holds the password for it
encrypted, the way it holds its pairwise salt, and the manage API never reads it back out — it can
only be written. A tenant with no server of its own mails through whatever the deployment
configured, and a deployment with no mailer either means invitations and password resets are links a
manager passes along by hand.
