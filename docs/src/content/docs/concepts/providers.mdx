---
title: Providers
description: A provider lets a person sign in with an account on another service over OpenID Connect, OAuth 2.0, or SAML.
---

A provider is another service that people can sign in with, such as Google, GitHub, Apple, or a
company's Okta or Entra, or any service that supports OpenID Connect, OAuth 2.0, or SAML 2.0. masks
links the account on the provider to an account in masks. That link is a **connected account**.

Applications can also use a provider on a person's behalf. See
[delegation](/concepts/delegation/).

A provider replaces a password only. It is never a second factor. A person who signs in with a
provider is still asked for an authenticator app or a passkey whenever their sign-in policy
requires one.

## Provider roles

Every provider has a role.

| | |
| --- | --- |
| `credential` | Another way to sign in to an account that already exists in masks. |
| `delegate` | The provider owns the account. |

A **credential** provider signs in only the account it is connected to, and it never creates an
account. When it confirms an address that belongs to an existing account, masks connects the two
only after that account signs in by another method and so proves it belongs to the same person. The
two stay connected after that.

A **delegate** provider does everything a credential provider does. It also creates an account for a
new person, and it updates the person's name, photo, and address from the provider's values on every
sign-in. Use a delegate provider when the company's directory is the source of truth for who works
there.

## Trusted email addresses

masks tells applications `email_verified: true`, so it accepts a provider's claim that an address
is confirmed only in specific cases. A provider is trusted for an address in either of two cases:

- The address is in one of the **email domains** listed for the provider.
- The provider is trusted to confirm addresses (`trusts_email`), and it reports this address as
  confirmed.

Turn on `trusts_email` only for a provider that verifies that a person controls the mailbox.
Google, Apple, GitHub, GitLab, Slack, LinkedIn, and Discord verify addresses, and their presets turn
`trusts_email` on. A self-hosted OpenID Connect server whose administrators can enter any address
does not verify addresses.

When a provider reports an address as unconfirmed, masks treats it as unconfirmed, even inside a
listed domain. SAML has no field for confirmation, so masks trusts a SAML provider only for
addresses in its listed domains.

When masks does not trust a provider for an address, a delegate provider creates no account for that
address, and a pending invitation for that address is not accepted. A person whom the provider
identifies with no address at all still gets an account, and that account has no address.

## Where a provider is offered

The sign-in policy for the client controls which providers appear:

- `first_factors` must include `provider` for any provider to be offered.
- `providers` lists the providers to offer. When it is unset, every provider is offered.
- masks hides a password or passkey option that the policy does not list, and refuses it if it is
  submitted anyway.
- When a policy's only first factor is `provider`, the sign-in page shows no identifier field. It
  shows only the provider buttons.

The console and the account page use the tenant's default policy, so that policy must keep a
password or a passkey. This keeps managers able to sign in when a provider is unavailable. Only a
client's own policy can restrict sign-in to providers.

## Connecting from the account page

A signed-in person can connect any provider that their default policy offers from their account
page. The connection uses the same callback URL the provider already has. masks requires that the
person signed in within the last fifteen minutes, and refuses an upstream account that is already
connected to a different person.

## Protocols

### OpenID Connect

The `id_token` identifies the person. masks checks its signature against the issuer's published
keys, and checks its issuer, audience, and nonce against the sign-in request that asked for it. The
request uses PKCE. The subject is `sub`, or `oid` for a Microsoft directory where the subject must
stay the same across applications.

### OAuth 2.0

For a provider that issues no `id_token`, masks reads the identity from the provider's userinfo
endpoint. `subject_claim` and `claims` map each claim to a path in the endpoint's response, for
example `data.id` for X and `id` for GitHub. The request uses PKCE, and masks discards the
provider's tokens as soon as it has read the profile.

An **emails URL** serves a provider that lists confirmed addresses separately from its public
profile, as GitHub does. masks uses the primary confirmed address from that list. It never uses an
address that appears only in the public profile.

### SAML 2.0

masks is the service provider. Setting up a SAML provider takes two steps:

1. Give the identity provider these two values from the provider's page in the console:

   | | |
   | --- | --- |
   | Assertion consumer service URL | `https://<tenant>/login/provider/<key>/callback` |
   | Service provider entity ID | `https://<tenant>/login/provider/<key>/metadata`, which also serves the masks metadata |

2. Give masks the identity provider's metadata, either as a URL or pasted in. masks fetches a
   metadata URL again every night, so it picks up a rotated certificate.

masks trusts an assertion only when all of these conditions hold:

- It is signed by a certificate in the identity provider's metadata.
- It answers the request this browser sent (`InResponseTo`).
- Its audience and recipient are this service provider.
- Its issuer is the identity provider's entity ID.
- The current time is within its validity window, allowing one minute of clock drift.

masks refuses an unsolicited, identity-provider-initiated response. A response cannot be replayed
into another sign-in, because masks marks the request it answers as used the first time.

Request a **persistent** name ID when the identity provider offers one. A transient name ID changes
on every sign-in, so every sign-in would appear to come from a new person.

### Apple

Apple's client secret is a short-lived ES256 token that masks signs with the key Apple issued. The
provider therefore stores a team ID, a key ID, and the `.p8` private key in place of a secret. Apple
posts its response back to masks, and it sends the person's name only on their first sign-in. masks
stores that name.

## Posted callbacks

Apple and SAML post their responses back across sites, and a browser does not send a
`SameSite=Lax` cookie with a cross-site POST. masks stores the posted parameters on the server for
five minutes under a one-time handle. It then redirects to the same URL as a GET request, which does
include the cookie, and the sign-in continues. Each handle can be redeemed once.

## Calling a provider's API

An application that must act for a person at a provider while that person is away, such as a
nightly sync or an agent, requests a [delegation](/concepts/delegation/). masks stores and
refreshes the provider's tokens.

An application that calls a provider only while the person is using it can run its own OAuth flow
with that provider. The `identities` scope tells the application which provider account to send the
person to. Userinfo lists each connected account, and the provider already recognizes the person,
so the flow is a redirect to the provider and back.

```json
{
  "sub": "8f4c…",
  "identities": [
    { "provider": "google", "protocol": "oidc", "sub": "10769150350006150715", "email": "ada@gmail.com" }
  ]
}
```

```
https://accounts.google.com/o/oauth2/v2/auth?…&login_hint=ada@gmail.com
```

masks never gives `identities` to a pairwise client. An upstream subject is the same for every
client, so it would let the client correlate a person that pairwise subjects keep separate.
