---
title: Exchanging a token
description: How a client exchanges a token for a narrower one that records who is acting for whom.
---

A token exchange ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)) issues one token in return
for another at `/token`. Some common uses:

- An API gateway gives a downstream service a token for that service only.
- An agent acting for a person holds a token that records that it acts for them.
- A backend exchanges the ID token that its browser frontend received for an access token of its
  own.

The client must be registered for `urn:ietf:params:oauth:grant-type:token-exchange`.

```sh
curl -u "$CLIENT_ID:$CLIENT_SECRET" https://demo.masks.example/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d subject_token="$ACCESS_TOKEN" \
  -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d scope="uris:catalog:read" \
  -d resource=https://uris.example/mcp
```

## What can be exchanged

| `subject_token_type` | |
| --- | --- |
| `urn:ietf:params:oauth:token-type:access_token` | a live access token this issuer signed |
| `urn:ietf:params:oauth:token-type:id_token` | an ID token this issuer signed, presented by the client it was issued to |

An exchange can only narrow a token. `scope`, `resource`, and `requested_lifetime` may each request
less than the subject token holds, and never more. The new token expires no later than the subject
token, whatever lifetime is requested. Revoking the subject token also revokes every token exchanged
from it.

An ID token has no scopes. Exchanging one grants at most the scopes the person consented to for
this client and the resources the client is registered for. The new token expires no later than
the ID token. The exchange is refused once the session the ID token was issued in has ended. A
client cannot exchange an ID token that was issued to another client, because that would let
anyone who obtained an ID token from a person's browser sign in as that person.

## Who is acting

Each access token issued by an exchange has an `act` claim that names the party holding it. The
claim nests the previous `act` claim, so the token records the whole chain of services:

```json
{
  "sub": "8b1f…",
  "client_id": "search-service",
  "act": { "sub": "search-service", "act": { "sub": "gateway" } }
}
```

A client that acts as a more specific party than itself presents that party's token as an
`actor_token`, with `actor_token_type`. The actor token must be live and issued to the client
presenting it. The `act` claim then names the actor token's subject and client. For example, an
agent that signs in as itself with [`client_credentials`](/concepts/clients/) and acts for a person
presents its own token as the actor token and the person's token as the subject token.

When a client exchanges an ID token that was issued to it, the client is acting for itself, so the
new token has no `act` claim unless an actor token was presented.

## A person's account at a provider

Requesting `urn:masks:params:oauth:token-type:upstream_access_token` returns the access token that
masks holds for the person at a provider, instead of a masks token. Much narrower rules apply. See
[delegation](/concepts/delegation/).

## What is not exchanged

masks does not exchange refresh tokens, SAML assertions, or tokens signed by another issuer. It
does not read a `may_act` claim in the subject token.
