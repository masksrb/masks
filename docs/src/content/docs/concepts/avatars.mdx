title: Avatars
description: Every actor has three faces at once — an uploaded photo, an identicon, and a two-letter mark — and a client picks the one it wants.
---

An actor does not choose an avatar style. They have all three, always, and the client picks which
one to draw.

`server/app/models/avatars.rb`, `avatar.rb`, `identicon.rb`, `initials.rb`

| Style | Where it comes from | Stored |
| --- | --- | --- |
| `photo` | uploaded, re-encoded to a 512px square WebP | one row per actor |
| `identicon` | a symmetric grid drawn from the actor's `uuid` | nothing |
| `initials` | two letters from `name`, else `nickname` | nothing |

Only the photo is stored. The other two are pure functions of columns the actor already has, drawn
as SVG on the way out, so they cost a hash and a string and cannot fall out of sync with the account.

## The endpoint

```
GET /avatars/:uuid                    the photo if you may see it, else the identicon
GET /avatars/:uuid/:style             one named style
GET /avatars/:uuid/:style/:digest     the same, immutable
GET /avatars/:uuid/:style?size=128    32, 64, 128, 256 or 512
```

The `uuid` is the `sub` the client already holds. A size outside the allowlist is clamped to the
next one up rather than honoured, so nobody can ask the server to resize to 40000 pixels.

The stamped form is content-addressed and answers `Cache-Control: immutable`. When the digest does
not match what the actor has now, the request **redirects** to the one that does — so a client
holding a month-old id token still draws a face, and lands on a URL it can cache forever.

## What the token carries

Every id token and every `/userinfo` response carries all three:

```json
{
  "sub": "0f8f...",
  "picture": "https://demo.auth.test/avatars/0f8f.../photo/9c1d4a2f5e6b7c80",
  "masks:avatars": {
    "photo": "https://demo.auth.test/avatars/0f8f.../photo/9c1d4a2f5e6b7c80",
    "identicon": "https://demo.auth.test/avatars/0f8f.../identicon/3b2a1c4d5e6f7089",
    "initials": "https://demo.auth.test/avatars/0f8f.../initials/7d6c5b4a39281706"
  }
}
```

`photo` is `null` when the actor has not uploaded one. `picture` is the standard OIDC claim and
resolves in order: the `picture_url` on the profile if the actor set one, then the photo, then the
identicon. So a client that only knows OIDC still gets a working image, and one that knows masks can
choose.

Discovery advertises the endpoint, which is how a client builds a URL for a subject it did not
receive a token for:

```json
{
  "avatar_endpoint": "https://demo.auth.test/avatars",
  "avatar_styles_supported": ["photo", "identicon", "initials"],
  "avatar_sizes_supported": [32, 64, 128, 256, 512]
}
```

## Who may see a photo

The generated styles are **public**. They are drawn from an opaque uuid the caller already holds and
say nothing a `sub` did not, and an `<img>` tag cannot carry an `Authorization` header — gating them
would mean every consumer proxies every avatar for no privacy gained.

A photo is a likeness of a person, so it is **gated**. It is released to:

- a bearer token carrying `profile` whose `sub` is the actor asked for,
- a bearer token carrying `masks:manage`,
- the actor's own browser session,
- an administrator's browser session, which is how the console draws them.

Anything else gets `401` with a `WWW-Authenticate` header. The bare `/avatars/:uuid` never refuses —
without the right to the photo it quietly serves the identicon instead, so an unauthenticated `<img>`
still draws something.

This means an application listing its users draws identicons for everyone and the real photo for the
person signed in. That is the honest consequence of the rule, not an oversight.

### Drawing a photo in a browser

An `<img>` cannot send a token, so the two client modes differ.

In session mode the backend already holds the token, and the engine proxies:

```erb
<img src="/auth/avatar" width="64" height="64" alt="">
```

```js
const auth = createSession({ basePath: "/auth" });
const account = await auth.session();

img.src = auth.avatarUrl(account, { size: 64 });
```

`avatarUrl` returns the local proxy path for the photo and the issuer's URL for a generated style,
so the token never reaches the page. The proxy passes a redirect back to the browser rather than
following it.

In browser mode the page holds the token, so the photo comes back as a blob:

```js
const blob = await auth.photo();

if (blob) img.src = URL.createObjectURL(blob);
else img.src = await auth.avatarUrl(subject, { style: "identicon" });
```

## Uploads

An upload is sniffed by magic bytes and refused unless it is PNG, JPEG, GIF or WebP — an SVG is not
an avatar, because serving a caller's SVG from the origin that holds the session cookie is a script
you did not write. What survives is re-encoded through libvips to a 512px square WebP with metadata
stripped, so none of the original file's bytes reach anyone: no EXIF, no GPS, no polyglot.

```ruby
Vips::Image.thumbnail_buffer(bytes, 512, height: 512, size: :both, crop: :attention)
           .webpsave_buffer(Q: 82, strip: true)
```

`crop: :attention` picks the salient region rather than the middle, which is usually the face.
Anything over 8MB, or with more than 100 megapixels in its header, is refused before decoding.

Smaller sizes are resized on demand and cached. The row holds the 512px original, its digest, and
nothing else:

```
avatars   tenant_id  actor_id  content_type  digest  byte_size  data
```

Tenant-scoped and under row-level security like every other table, so the bytes cannot leak across
tenants even if the Ruby scope is wrong.

## Where they show up

The account page draws all three and takes the upload. The console draws one in the actor list and
all three on an actor, where an administrator can remove a photo but never set one — a photo is the
actor's to upload, and an admin who could set one could impersonate them in every application's UI.
