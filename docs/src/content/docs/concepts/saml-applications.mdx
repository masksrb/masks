---
title: SAML applications
description: Signing people into an application that only speaks SAML 2.0, with masks as its identity provider.
---

Some applications, such as wikis, ticketing systems, and cloud consoles, sign people in only over
SAML 2.0. masks acts as the identity provider for these applications. The application sends the
person to masks with an `AuthnRequest`. masks signs the person in the same way it signs in anyone
else, with the tenant's [sign-in policy](/concepts/tenants/), second factors, and passkeys. masks then
posts a signed assertion back to the application.

Signing in to masks through another organization's SAML identity provider is the opposite direction.
That is configured as a [provider](/concepts/providers/).

## What to give the application

| | |
| --- | --- |
| metadata | `https://demo.masks.example/saml/metadata` |
| entity ID | the same URL |
| single sign-on | `https://demo.masks.example/saml/sso`, HTTP-Redirect or HTTP-POST |
| certificate | in the metadata, as a self-signed certificate for each of the tenant's signing keys |

Most applications need only the metadata URL. masks builds the certificate from the key it signs
tokens with. After a [key rotation](/concepts/keys/), the application has to read the metadata again.
The retiring key's certificate stays in the metadata during the overlap.

## Registering one

To register a SAML application:

1. In `/manage`, open **Clients → Add client → SAML app**.
2. Paste the application's own metadata.
3. Click **Read it**. masks fills in the application's entity ID, its HTTP-POST assertion consumer
   services, and the certificate it signs requests with.

A SAML application is an approved client with no grants and no secret. It cannot be used at
`/authorize` or `/token`, and the code that authenticates OAuth clients never matches it.

| | |
| --- | --- |
| entity ID | the value its `AuthnRequest` names as `Issuer` |
| assertion consumer services | the only URLs masks posts an assertion to |
| names people by | a persistent identifier (pairwise if the client is pairwise), or their email |
| refuse unsigned requests | check every request against the application's certificate |
| let people start from masks | answer `/saml/initiate/<client_id>` without a request |

## What is checked

masks refuses a request on an error page, and posts nothing to the application, when any of the
following is true:

- No application is registered under the request's `Issuer`.
- Its `AssertionConsumerServiceURL` is not one of the application's, or it asks for a binding other
  than HTTP-POST.
- It asks for a NameID format that masks does not issue.
- It was made more than eight minutes ago (a five-minute lifetime plus three minutes of clock skew),
  it was made more than three minutes in the future, or it is addressed to another `Destination`.
- masks has already received it.
- Any `ID` in it appears twice.
- The application signs its requests, and this request's signature does not verify with SHA-256 or
  stronger, or the request contains a second signature. A redirect is signed on the query string. A
  post is signed with a signature enveloped in the XML.
- Any parameter is sent twice, or the request is larger than 64 KB.
- It declares a document type. A document type declaration is how XML external entities are
  introduced.

`ForceAuthn` makes the person sign in again. `IsPassive` returns a `NoPassive` status without
showing the person any page. When masks refuses the person, because they are suspended, they
decline, or the sign-in policy stops them, masks posts a `RequestDenied` status to the application in
place of an assertion.

## What is asserted

masks signs both the response and the assertion inside it with RSA-SHA256. The assertion:

- is addressed to the application's entity ID.
- is confirmed for the application's assertion consumer service and the request's `ID`.
- is valid for five minutes.
- names the session in its `SessionIndex`.
- names `https://refeds.org/profile/mfa` as the authentication context when the person used a
  second factor.

masks releases attributes under their claim names: `email`, `name`, `given_name`, `family_name`, and
`preferred_username`. The application's `samlAttributes` setting can map its own attribute names to
claims instead. masks releases only the claims that the person's `openid profile email` consent
covers.

masks releases an email only after the person has confirmed it. This applies both to the email
attribute and to the NameID when the application names people by email. Most applications match
accounts by email, so an unconfirmed email would let someone sign in to another person's account in
that application. The page that posts the assertion has a content security policy that allows only
its own script to run.

## Not yet supported

masks does not yet support single logout, encrypted assertions, the artifact binding, or choosing an
assertion consumer service by index.
