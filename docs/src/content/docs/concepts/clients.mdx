---
title: Clients
description: An application registered against a tenant.
---

A client is an application allowed to start a sign-in, or to sign in as itself. It holds redirect
URIs, the resources it speaks for, and the scopes it may ask for.

## How one gets here

Three ways, and the console shows which:

- **added** — a manager adds it from the console, and it is approved by them as it is created. Its
  secret is shown once.
- **approved** — a person completed the `/handshake` flow and the credentials came back server to
  server. Nothing was pasted between the two.
- **self-registered** — RFC 7591 dynamic registration. Bounded by the tenant's ceiling, and never
  granted a `masks:` scope.

Only an approved client may hold a reserved `masks:` scope. That is what stops a stranger's
connector registering itself with administrative reach — and why only an approved client can be
let use somebody's account elsewhere through a [delegation](/concepts/delegation/).

## Signing in as itself

A service with nobody behind it — an indexer, a nightly job, a worker — asks the token endpoint for
a token of its own with `client_credentials`:

```sh
curl -u "$CLIENT_ID:$CLIENT_SECRET" https://demo.masks.example/token \
  -d grant_type=client_credentials \
  -d scope="uris:catalog:read" \
  -d resource=https://uris.example/mcp
```

Only an approved client that authenticates may be given the grant. A self-registered client never
is, and neither registration management nor a handshake can add it: a manager switches it on.
Without that, anybody able to register could hand themselves any scope a resource server honours.

The token's `sub` is the client's own `client_id`, as RFC 9068 asks, and `client_id` names it again.
It carries only the scopes that do not speak for a person — never `openid`, `profile`, `email`,
`offline_access`, `identities`, `masks:manage`, `masks:handshake` or a delegation — so it is refused
at userinfo and at the manage API. No refresh token is issued; the service asks again. Its audience
is narrowed to the client's resources, and it can be held to a DPoP key like any other.

A resource server tells the two apart by comparing `sub` with the `client_id` it knows: a person's
`sub` is never a client's. When the token is [exchanged](/concepts/delegation/) onward, `sub` keeps
naming the service it started with and `act` names who holds it now.

## Scopes

| | |
| --- | --- |
| `required_scopes` | always granted, never shown on a consent screen |
| `allowed_scopes` | everything else it may ask for |

## Consent

Every person is asked, once, before a client is granted anything on their behalf. What they approve
is remembered, and they are asked again only when the client wants more, or passes
`prompt=consent`.

Approving a handshake counts as the approver's consent, and is recorded as one, so the approver is
not asked twice. It says nothing about anybody else: a colleague who signs in to the same client
sees the consent screen as they would for any other client.

`consent_required` is on for every client. A manager may switch it off for an approved client — a
first-party application nobody should be asked about — and then nobody is shown the screen unless
the client asks with `prompt=consent`. A self-registered client always asks.

## Who it thinks it is talking to

`subject_type` decides what a client is told about a person.

| | |
| --- | --- |
| `public` | the actor's own identifier — every client sees the same `sub` |
| `pairwise` | one derived for this client's sector, and nobody else's |

Two pairwise clients cannot tell they are looking at the same person by comparing subjects, and the
avatar URLs in the token carry the pairwise subject too, so nothing else in the payload gives the
person away.

The sector is the host of the redirect URIs by default. A client whose redirect URIs span more than
one host needs a `sector_identifier_uri` instead — an `https` URL holding a JSON array of every
redirect URI it uses. masks reads it at registration and refuses the client unless the document
names them all, which is what stops one client claiming another's sector and correlating its
people. Clients that share a sector share subjects, deliberately: that is how a suite of
applications sees one identity.

A pairwise subject is minted once and kept, so it holds steady across sign-ins, and it is
tenant-local — the same string means nothing in another tenant.

## Secrets and archiving

`token_endpoint_auth_method` is `client_secret_basic`, `client_secret_post`, or `none` for a public
client with no secret to rotate. Rotating issues a new secret and the old one stops working
immediately.

Archiving is the end of a client — it can no longer sign anybody in — but it is not a delete, and
any [namespace](/concepts/namespaces/) it claimed survives until released.
