---
title: Signing keys
description: One keypair per tenant, rotated with an overlap rather than a cutover.
---

Every tenant generates its own RSA keypair when it is created. The private half is encrypted at
rest; the public half is published as a JWK at that tenant's JWKS endpoint and nowhere else.

That is what makes tenant isolation fail loudly: a token minted for one tenant carries a `kid` the
next tenant's JWKS does not list, so verification refuses rather than quietly accepting it.

## States

| State | |
| --- | --- |
| `staged` | published at JWKS, signing nothing yet |
| `active` | signing every new token |
| `retiring` | no longer signing, still verifying |
| `retired` | done |

## Rotating

Staging first is the point. A client that caches JWKS sees the new key *before* anything is signed
with it, so activation does not race the cache.

- **Stage** publishes a key ahead of time. Only one may be staged at a time, and a staged key can be
  discarded because nothing has been signed with it.
- **Activate** makes a staged key the signing key. The outgoing one keeps verifying for 24 hours.
- **Rotate** does both at once, for when there is no time to wait.

A key that is already signing cannot be activated again, and a signing key cannot be discarded.
