---
title: Signing keys
description: One RSA keypair per tenant, published only at that tenant's JWKS endpoint.
---

`server/app/models/signing_key.rb`

Every tenant generates a keypair when it is created (`Tenant` `after_create`). `private_pem` is
encrypted at rest; `public_jwk` is published as a JWK at that tenant's JWKS endpoint and no other.

| | |
| --- | --- |
| `SigningKey::SIZE` | 2048 |
| `SigningKey::ALGORITHM` | `RS256` |
| `SigningKey::OVERLAP` | 24 hours |

```
GET https://demo.auth.example/.well-known/jwks.json
{"keys":[{"kty":"RSA","use":"sig","alg":"RS256","kid":"e9914114-…","n":"…","e":"AQAB"}]}
```

`kid` is a UUID generated with the key.

## Why the signature layer

The three isolation layers fail differently — see [Tenancy](/concepts/tenancy). Application scopes
fail by omission; row-level security fails silently if the connecting role is a superuser. A
per-tenant key cannot fail quietly:

```
{"error":"invalid_token",
 "error_description":"Could not find public key for kid e9914114-08c3-438b-a4f4-d71b70489bde"}
```

There is no code path where the wrong tenant considers the token and decides against it. The key
that signed it was never published where they could look.

:::caution[Not retrofittable]
A single installation-wide key cannot be split into per-tenant keys later without invalidating every
token in flight and rewriting every stored `kid`.
:::

## Scopes

| | |
| --- | --- |
| `SigningKey.active` | `retired_at IS NULL` and activated — what signing uses |
| `SigningKey.staged` | `activated_at IS NULL` and not retired — published, signing nothing |
| `SigningKey.published` | `retired_at IS NULL OR retired_at > now()` — what JWKS lists |

`published` is deliberately wider than `active` at both ends: it carries a staged key that has not
started signing and a key retiring in the future. That gap in both directions is what lets a key
change hands without a token failing to verify.

Every key is therefore in one of four states, which is what `/manage` badges:

| | |
| --- | --- |
| `staged` | published, signing nothing |
| `active` | signing every new token |
| `retiring` | `retired_at` is set but in the future — still published, no longer signing |
| `retired` | past `retired_at`, no longer published, awaiting `CleanupJob` |

## Rotation

```ruby
SigningKey.rotate!(tenant: tenant)
```

Mints a replacement, activates it immediately, and sets `retired_at` on the outgoing key to
`OVERLAP.from_now` rather than now. The outgoing key keeps being published for 24 hours, so tokens
signed just before the rotation still verify while nothing new is signed with it.

`CleanupJob` deletes keys past their retirement — see [Hardening](/concepts/hardening).

The Ruby client refetches JWKS once on an unknown `kid`, so a rotation is picked up without a
restart. See [Verify a token](/guides/verifying).

## Staging

A client that caches JWKS and does not refetch on an unknown `kid` will reject tokens signed by a key
it has never seen. Staging is rotation split in two, so that client is never surprised:

```ruby
key = SigningKey.stage!(tenant: tenant)   # published, signing nothing
key.activate!                             # signs from here, incumbent retires after OVERLAP
```

Between the two calls the JWKS endpoint lists both keys and the incumbent keeps signing. Leave the
gap longer than the longest cache any client holds, and the changeover costs no failed verification
at either edge.

## From the console

Settings carries the four mutations. `stageSigningKey` and `activateSigningKey` are the two halves
above, `discardSigningKey` drops a staged key that nothing has signed with, and `rotateSigningKey` is
the immediate path for a key you believe is compromised.

| | |
| --- | --- |
| `stageSigningKey` | refused if a key is already staged |
| `activateSigningKey(kid:)` | refused unless that key is staged |
| `discardSigningKey(kid:)` | refused unless that key is staged |
| `rotateSigningKey` | always available |
