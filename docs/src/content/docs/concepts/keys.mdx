---
title: Signing keys
description: One RSA keypair per tenant, published only at that tenant's JWKS endpoint.
---

`server/app/models/signing_key.rb`

A tenant generates a keypair on `after_create_commit`. `private_pem` is encrypted at rest.
`public_jwk` is published as a JWK at that tenant's JWKS endpoint and nowhere else.

| | |
| --- | --- |
| `SigningKey::SIZE` | 2048 |
| `SigningKey::ALGORITHM` | `RS256` |
| `SigningKey::OVERLAP` | 24 hours |

```
GET https://demo.auth.example/.well-known/jwks.json
{"keys":[{"kty":"RSA","use":"sig","alg":"RS256","kid":"e9914114-…","n":"…","e":"AQAB"}]}
```

`kid` is a UUID generated with the key.

## Why keys are per tenant

Of the three isolation layers described in [Tenancy](/concepts/tenancy), application scopes fail by
omission and row-level security fails silently when the connecting role is a superuser. A per-tenant
key fails loudly:

```
{"error":"invalid_token",
 "error_description":"Could not find public key for kid e9914114-08c3-438b-a4f4-d71b70489bde"}
```

The wrong tenant never evaluates the token at all. The key that signed it was never published where
that tenant would look.

:::caution[Not retrofittable]
Splitting an installation-wide key into per-tenant keys invalidates every token in flight and
requires rewriting every stored `kid`.
:::

## Scopes

| | |
| --- | --- |
| `SigningKey.active` | activated, `retired_at IS NULL` — what signing uses |
| `SigningKey.staged` | `activated_at IS NULL` and not retired — published, signing nothing |
| `SigningKey.published` | `retired_at IS NULL OR retired_at > now()` — what JWKS lists |

`published` is wider than `active` at both ends. It carries a staged key that has not started
signing, and a key retiring in the future. That overlap is what lets a key change hands without a
token failing to verify.

Every key is in one of four states, which `/manage` badges:

| | |
| --- | --- |
| `staged` | published, signing nothing |
| `active` | signing every new token |
| `retiring` | `retired_at` set in the future — still published, no longer signing |
| `retired` | past `retired_at`, no longer published, awaiting `CleanupJob` |

## Rotation

```ruby
SigningKey.rotate!(tenant: tenant)
```

Mints a replacement, activates it, and sets `retired_at` on the outgoing key to `OVERLAP.from_now`.
The outgoing key stays published for 24 hours, so tokens signed just before the rotation still
verify.

`CleanupJob` deletes keys past their retirement. See [Hardening](/concepts/hardening).

The Ruby client refetches JWKS once on an unknown `kid`, so a rotation is picked up without a
restart. See [Verify a token](/guides/verifying).

## Staging

A client that caches JWKS and does not refetch on an unknown `kid` will reject tokens signed by a
key it has never seen. Staging splits rotation in two:

```ruby
key = SigningKey.stage!(tenant: tenant)   # published, signing nothing
key.activate!                             # signs from here, incumbent retires after OVERLAP
```

Between the two calls, JWKS lists both keys and the incumbent keeps signing. Leave a gap longer than
the longest cache any client holds and the changeover costs no failed verification.

## From the console

Settings carries four mutations. `stageSigningKey` and `activateSigningKey` are the two halves
above, `discardSigningKey` drops a staged key, and `rotateSigningKey` is the immediate path for a
key you believe is compromised.

| | |
| --- | --- |
| `stageSigningKey` | refused if a key is already staged |
| `activateSigningKey(kid:)` | refused unless that key is staged |
| `discardSigningKey(kid:)` | refused unless that key is staged |
| `rotateSigningKey` | always available |
