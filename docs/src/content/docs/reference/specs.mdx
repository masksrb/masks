---
title: OIDC and OAuth
description: The specifications masks implements, and how far each one goes.
---

masks is an OpenID Connect provider before it is anything else. This is every specification it
speaks, what part of it is implemented, and — where it matters more — what part is not.

Both OpenID Foundation certification plans pass: `oidcc-config` and `oidcc-basic`, 2,213
conditions, zero failures. `./dev conformance` runs them against a local server.

## The core

| | | |
| --- | --- | --- |
| [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) | ✅ | authorization code flow, ID tokens, userinfo, `prompt`, `max_age`, `acr`/`amr`, the `claims` parameter |
| [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) | ✅ | `/.well-known/openid-configuration`, per-tenant |
| [OpenID Connect Dynamic Registration 1.0](https://openid.net/specs/openid-connect-registration-1_0.html) | ✅ | bounded by the tenant's ceiling |
| [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) — OAuth 2.0 | ◐ | `authorization_code`, `refresh_token` and `client_credentials`. No implicit, no password |
| [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750) — Bearer tokens | ✅ | header only, never a query parameter |
| [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519) — JWT | ✅ | `RS256`, a signing key per tenant. ID tokens are typed `JWT`, access tokens `at+jwt` and logout tokens `logout+jwt` |
| [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517) — JWK | ✅ | `/.well-known/jwks.json`, staged and retired keys published through a rotation |

Response types are `code` and only `code`. Response modes are `query` and only `query`.

| [RFC 9101](https://www.rfc-editor.org/rfc/rfc9101) — Request objects (JAR) | ✗ | `request` and `request_uri` are refused, and discovery says so |

## Client authentication

`client_secret_basic`, `client_secret_post`, `private_key_jwt`
([RFC 7523](https://www.rfc-editor.org/rfc/rfc7523), signed with RSA, RSA-PSS or ECDSA, against
`jwks` or a `jwks_uri`), and `none` for a public client — see [clients](/concepts/clients/).
`client_secret_jwt` is not offered, because masks holds only a hash of a secret, and mTLS
([RFC 8705](https://www.rfc-editor.org/rfc/rfc8705)) is not implemented.

## What ✅ and ◐ mean here

✅ means the specification is implemented and covered by the test suite, and where a conformance
plan exists, that it passes. ◐ means the part of it masks needs is implemented and the rest is
named above rather than left for you to discover. ✗ means it is not there, and the server says so
in its discovery document rather than failing quietly when you try.
