---
title: OIDC and OAuth
description: The specifications masks implements, and how far each one goes.
---

masks is an OpenID Connect provider. This page lists every specification it
implements, the parts it implements, and the parts it leaves out.

Both OpenID Foundation certification plans, `oidcc-config` and `oidcc-basic`,
pass with 2,213 conditions and no failures. `./dev conformance` runs them
against a local server.

In the tables below, ✅ means the specification is implemented and covered by the
test suite, and that its conformance plan passes where one exists. ◐ means masks
implements the parts it needs, and the Coverage column names the parts it leaves
out. ✗ means masks does not implement it, and the discovery document says so.

## Core

| Specification | Status | Coverage |
| --- | --- | --- |
| [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) | ✅ | The authorization code flow, ID tokens, userinfo, `prompt`, `max_age`, `acr` and `amr`, and the `claims` parameter. |
| [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) | ✅ | `/.well-known/openid-configuration`, one for each tenant. |
| [OpenID Connect Dynamic Registration 1.0](https://openid.net/specs/openid-connect-registration-1_0.html) | ✅ | Bounded by the tenant's ceiling. |
| [OAuth 2.0 (RFC 6749)](https://www.rfc-editor.org/rfc/rfc6749) | ◐ | The `authorization_code`, `refresh_token`, and `client_credentials` grants. The implicit and password grants are not offered. |
| [Bearer tokens (RFC 6750)](https://www.rfc-editor.org/rfc/rfc6750) | ✅ | The userinfo endpoint reads a bearer token from the `Authorization` header, a form-encoded body, or the `access_token` query parameter. |
| [JWT (RFC 7519)](https://www.rfc-editor.org/rfc/rfc7519) | ✅ | `RS256`, with a signing key for each tenant. ID tokens are typed `JWT`, access tokens `at+jwt`, and logout tokens `logout+jwt`. |
| [JWK (RFC 7517)](https://www.rfc-editor.org/rfc/rfc7517) | ✅ | `/.well-known/jwks.json`, which also publishes staged and retired keys during a rotation. |

The only response type is `code`, and the only response mode is `query`.

## Hardening

| Specification | Status | Coverage |
| --- | --- | --- |
| [PKCE (RFC 7636)](https://www.rfc-editor.org/rfc/rfc7636) | ✅ | `S256` only. Every public client must send a challenge. |
| [Pushed authorization requests (RFC 9126)](https://www.rfc-editor.org/rfc/rfc9126) | ✅ | A client can be required to use them. See [pushed requests](/guides/security/#pushed-requests). |
| [DPoP (RFC 9449)](https://www.rfc-editor.org/rfc/rfc9449) | ✅ | Includes `dpop_jkt`, bound refresh tokens, and `dpop_bound_access_tokens`. See [binding a token with DPoP](/guides/security/#binding-a-token-with-dpop). |
| [Issuer identification (RFC 9207)](https://www.rfc-editor.org/rfc/rfc9207) | ✅ | `iss` on every authorization response. |
| [Resource indicators (RFC 8707)](https://www.rfc-editor.org/rfc/rfc8707) | ✅ | `resource` narrows the audience at both the authorization and token endpoints. |
| [Request objects, JAR (RFC 9101)](https://www.rfc-editor.org/rfc/rfc9101) | ◐ | A signed `request` at `/authorize` and `/par`, and a client can be required to sign. See [signed requests](/guides/security/#signed-requests). The only `request_uri` accepted is one issued by `/par`. Encrypted request objects are not read. |
| [FAPI 2.0](https://openid.net/specs/fapi-security-profile-2_0-final.html) | ◐ | PAR, PKCE, `private_key_jwt`, DPoP, `iss` on the response, and signed requests are all implemented, and a client can be required to use each one. The FAPI certification plan has not been run. |

## Sessions

| Specification | Status | Coverage |
| --- | --- | --- |
| [Back-channel logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html) | ✅ | Signed logout tokens. Delivery is attempted up to five times, and a delivery that still fails is recorded as an event. |
| [RP-initiated logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html) | ✅ | `end_session_endpoint`. |
| [Front-channel logout 1.0](https://openid.net/specs/openid-connect-frontchannel-1_0.html) | ✗ | Discovery sets `frontchannel_logout_supported` to `false`. |
| [Session management 1.0](https://openid.net/specs/openid-connect-session-1_0.html) | ✗ | Not planned. The iframe it depends on no longer works in current browsers. Discovery has no `check_session_iframe`. |

## Identity

| Specification | Status | Coverage |
| --- | --- | --- |
| Pairwise subject identifiers | ✅ | Includes a verified `sector_identifier_uri`. See [subject identifiers](/guides/client-features/#subject-identifiers). |
| [WebAuthn Level 2](https://www.w3.org/TR/webauthn-2/) | ✅ | Passkeys, as a first factor or a second factor. |
| [TOTP (RFC 6238)](https://www.rfc-editor.org/rfc/rfc6238) | ✅ | With backup codes. |
| [SCIM 2.0](https://www.rfc-editor.org/rfc/rfc7644) | ◐ | `/Users` with filters, `PATCH`, ETags, and suspension, and the discovery endpoints. See [provisioning](/guides/sso-saml/#provisioning). Groups, bulk operations, and sorting are not implemented. |
| SAML 2.0 | ◐ | Both directions. A SAML identity provider can sign people in to masks (see [providers](/guides/sso-saml/#providers)), and masks signs people in to SAML applications over HTTP-Redirect and HTTP-POST, checking signed requests (see [SAML applications](/guides/sso-saml/#saml-applications)). Single logout and encrypted assertions are not implemented. |

## Client authentication

masks accepts these token endpoint authentication methods:

|                       |                                                                                                                  |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `client_secret_basic` | The secret in an HTTP Basic `Authorization` header. The default for a client added in the console.              |
| `client_secret_post`  | The secret in the form body.                                                                                     |
| `private_key_jwt`     | A JWT assertion ([RFC 7523](https://www.rfc-editor.org/rfc/rfc7523)) signed with RSA, RSA-PSS, or ECDSA, checked against the client's `jwks` or `jwks_uri`. |
| `none`                | A public client, which must use PKCE.                                                                            |

See [client authentication](/guides/client-features/#client-authentication) for how each is configured.

`client_secret_jwt` is not offered, because masks stores only a hash of a client
secret. Mutual TLS ([RFC 8705](https://www.rfc-editor.org/rfc/rfc8705)) is not
implemented.
