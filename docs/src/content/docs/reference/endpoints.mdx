`server/config/routes.rb`

All of these are per tenant. The tenant is resolved from the hostname, so `demo.auth.example/token`
and `acme.auth.example/token` are different endpoints with different keys.

## Discovery

| Route | |
| --- | --- |
| `GET /.well-known/openid-configuration` | the discovery document, including the `tenant` identity |
| `GET /.well-known/oauth-authorization-server` | the same document, for clients that look there |
| `GET /.well-known/jwks.json` | this tenant's published keys |
| `GET /.well-known/oauth-protected-resource(/*resource)` | RFC 9728 metadata for `/manage` and `/connections` |

`Issuer#discovery` names `handshake_endpoint` and `masks_protocol_version` alongside the standard
fields, so an application discovers where to ask to be connected rather than writing the path down.

Four fields are worth reading before writing a client:

| | |
| --- | --- |
| `acr_values_supported` | `urn:masks:acr:pwd`, `urn:masks:acr:mfa` |
| `claims_parameter_supported` | `true` |
| `request_parameter_supported` | `false` |
| `request_uri_parameter_supported` | `false` |

The last two are declared rather than left to default, because `/authorize` **refuses** a `request`
or `request_uri` with `request_not_supported` / `request_uri_not_supported` rather than ignoring it.
Reading the query and skipping the object would let unsigned parameters beat the ones the client
signed.

Also published: `grant_types_supported` (`authorization_code`, `refresh_token`, token exchange),
`code_challenge_methods_supported` (`S256` only), `token_endpoint_auth_methods_supported`
(`client_secret_basic`, `client_secret_post`, `none`), `response_modes_supported` (`query`) and
`authorization_response_iss_parameter_supported`.

## Flow

| Route | |
| --- | --- |
| `GET POST /authorize` | starts the code flow; redirects to sign-in or consent as needed |
| `POST /token` | `authorization_code`, `refresh_token`, and token-exchange grants |
| `POST /revoke` | RFC 7009 — revokes a token and everything exchanged from it |
| `POST /introspect` | RFC 7662 |
| `GET POST /userinfo` | claims for the bearer, requires the `openid` scope |
| `GET /avatars/:uuid/:style` | an actor's [avatar](/concepts/avatars/); generated styles are public, a photo is gated |

### `/authorize` parameters

| | |
| --- | --- |
| `response_type` | `code` |
| `client_id` `redirect_uri` | must match a registered URI exactly |
| `scope` | narrowed to what the client is registered for |
| `state` | echoed back; you must check it |
| `nonce` | bound into the id token |
| `code_challenge` `code_challenge_method` | `S256`; required for public clients |
| `resource` | RFC 8707; may repeat |
| `prompt` | `login` forces re-authentication, `consent` re-asks, `none` refuses to interact |
| `max_age` | a ceiling on how long ago the person signed in, checked against `auth_time` |
| `acr_values` | space-separated; the id token's `acr` names which was used |
| `claims` | JSON, OIDC Core 5.5; `userinfo` claims are released by name |

Both methods take the same parameters. `POST` is form-encoded, and a repeated `resource` may arrive
in the body as well as the query.

The redirect back always carries `iss`, so a client with several issuers can tell which answered.

```
&claims={"userinfo":{"name":{"essential":true}}}
```

Essential and voluntary are treated alike — masks releases what it holds either way, because
refusing a voluntary request only teaches a client to ask for the broader scope instead.

## Sign-in

| Route | |
| --- | --- |
| `GET POST DELETE /login` | the [login machine](/concepts/login) — every prompt posts here |
| `GET POST DELETE /logout` | revokes the session |
| `GET /` | the account page: who you are, and what you have authorized |

There is one sign-in endpoint, not one per factor. `LoginsController#update` takes an `event` and
the updates a state `accepts`, and answers HTML or JSON from one code path.

## Connections

Upstream identity providers a tenant configures — the credential broker.

| Route | |
| --- | --- |
| `GET /connections` | what this actor has connected |
| `GET POST /connections/:provider/start` | begin the upstream flow |
| `GET /connections/:provider/callback` | finish it |
| `DELETE /connections/:id` | revoke one |
| `POST /connections/token` | release a live upstream access token to a bearer holding `masks:connections:<provider>` |

`/connections/token` is what lets a downstream service use an account on the person's behalf without
ever holding the upstream refresh token. Rate limited to 120 per minute.

## Manage

| Route | |
| --- | --- |
| `POST /manage/graphql` | the administration API — requires `masks:manage` |
| `GET /manage(/*path)` | the administration UI |

`server/app/graphql/manage/mutations/`: `createActor`, `resendInvitation`, `resetPassword`,
`verifyEmail`, `updateActor`, `setActorScopes`, `signOutActor`, `deleteActor`,
`generateBackupCodes`, `disableAuthenticator`, `revokePasskey`, `removeAvatar`, `updateClient`,
`rotateClientSecret`, `archiveClient`, `revokeSession`, `blockDevice`, `unblockDevice`,
`signOutDevice`, `updateTenant`, `stageSigningKey`, `activateSigningKey`, `discardSigningKey`,
`rotateSigningKey`.

`deleteActor` takes the account and everything hanging off it — sessions, tokens, consents,
passkeys, connections, avatar — and refuses on the actor holding the token, who would be locking
themselves out. `signOutActor` ends every session and refresh token without touching the password.

## Errors

OAuth error codes, as JSON:

```json
{ "error": "invalid_grant", "error_description": "that code is not valid or has expired" }
```

Errors raised after the client and its `redirect_uri` are established come back at the redirect URI.
Errors about the client or the redirect URI itself never do — see [policies](/concepts/policies).

When there is nowhere safe to send the error, `/authorize` renders an HTML page naming the code and
what it means. A caller that does not ask for HTML still gets the JSON body.

`401` responses carry a `WWW-Authenticate` header. `/userinfo` accepts its bearer token in the
`Authorization` header or as an `access_token` form parameter per RFC 6750, and refuses with
`invalid_request` when both arrive at once.
