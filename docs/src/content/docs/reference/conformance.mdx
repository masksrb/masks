title: Conformance
description: masks runs the OpenID Foundation's certification plans, not only tests written here.

The OpenID Foundation publishes certification plans written against the specification. masks runs
two of them.

```
oidcc-config-certification-test-plan     2 modules ·   35 conditions · 0 failures
oidcc-basic-certification-test-plan     39 modules · 2178 conditions · 0 failures
```

Registration is dynamic, so the suite registers its own clients and there is no static setup to keep
in step.

## Running it

```sh
bin/conformance          # up, then run both plans
bin/conformance up       # just stand the stack up
bin/conformance logs     # follow the suite server
bin/conformance down     # tear down, including volumes
bin/conformance plans    # print which plans run
```

It wants Docker and about twelve minutes. The stack is masks behind a Caddy TLS proxy on a Docker
network, alongside the Foundation's suite and the Mongo it needs. The suite image is pulled at a
pinned release rather than built from source.

| | Default |
| --- | --- |
| `SUITE_REF` | `release-v5.2.4` |
| `SUITE_PORT` | `8443` |

The plans, from `bin/conformance`:

```
oidcc-config-certification-test-plan
oidcc-basic-certification-test-plan[server_metadata=discovery][client_registration=dynamic_client]
```

Exports and a full log land in `conformance/results/`. `.github/workflows/conformance.yml` runs the
same thing nightly; on a pull request it runs only when the PR carries the `conformance` label,
because it wants Java, Mongo and a container build.

:::note[This is where `MASKS_PUBLIC_ORIGIN_TEMPLATE` gets exercised]
The suite reaches masks through a proxy under a different origin than the app binds, which is
exactly the seam that template exists for — and the only place it is currently tested.
:::

## Reading a result

| | |
| --- | --- |
| `PASSED` | every condition held |
| `SKIPPED` | masks declares it does not support the feature, so the plan skips it |
| `REVIEW` | every automated condition held; a human signs off a screenshot at certification |
| `FAILED` | a real defect |

`SKIPPED` is a correct outcome, not a gap. `conformance/expected-skips.json` names each one:

| Module | Skips because |
| --- | --- |
| `oidcc-idtoken-unsigned` | only `RS256` is advertised, so a client cannot register `alg: none` |
| `oidcc-scope-address` · `oidcc-scope-phone` · `oidcc-scope-all` | masks defines four scopes, and `address` and `phone` are not among them |
| `oidcc-request-uri-unsigned-…` · `oidcc-unsigned-request-object-…` | `request` and `request_uri` are declared unsupported and **refused**, which is the outcome those module names allow for |

A server that ignored `request` rather than refusing it would fail rather than skip.

`REVIEW` covers the four modules whose remaining step is a person looking at a screenshot: the two
that force re-authentication, and the two that show an error page for an unregistered
`redirect_uri`. The browser config captures those screenshots automatically, so the modules complete
rather than hanging.

## Expected divergence

`conformance/expected-failures.json` names each deliberate deviation with the module, the condition,
and why. It carries two, both additive and both ignorable by a spec-conformant client:

| | |
| --- | --- |
| the `tenant` claim | in the id token and the discovery document — the reason a consumer never calls back to learn which tenant answered |
| `resource_indicators_supported` | in metadata, which RFC 8414 does not register |

Keeping them in that file rather than in someone's memory is what lets a warning that is a decision
read differently from a warning that is a bug.

## What it caught

None of this was visible to the server's own suite, which was green throughout:

- a `request` object **ignored** rather than refused, so the `state` and `nonce` a client had signed
  lost to the unsigned ones beside them
- `POST /authorize` not routed at all
- a replayed authorization code leaving the access token it had already issued alive
- the id token carrying claims that belong at [userinfo](/concepts/tokens)
- a client registered through DCR unable to ask for `offline_access`
- `unsupported_grant_type` and `invalid_client` both answering `invalid_request`
