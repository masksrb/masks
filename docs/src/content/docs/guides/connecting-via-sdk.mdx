An app connects to masks with one of six SDKs. An SDK (software development kit) is a library that
masks publishes for one language. With an SDK, an app:

- registers itself through a handshake
- signs people in
- acts for a person at another provider
- trades a token for a narrower one

## Choosing an SDK

Pick the SDK for the place your app runs. Each language's guide walks through the handshake,
sign-in, and checking tokens.

| SDK                                              | For                                                                                                                                     |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| [`Masks::Rails`](/reference/ruby/rails/)         | A Rails app. An engine that mounts sign-in, the handshake, and token checks. See [Rails apps](/reference/ruby/).                        |
| [`Masks::Client`](/reference/ruby/client/)       | Any Ruby process. `Masks::Rails` is built on it.                                                                                        |
| [`@masks/client`](/reference/javascript/client/) | A single-page app, in the browser. See [static sites](/reference/javascript/static/).                                                   |
| [`@masks/server`](/reference/javascript/server/) | A JavaScript server: Next.js, Auth.js, Express, Hono, or any app that takes a `Request`. See [JavaScript apps](/reference/javascript/). |
| [`masks-client`](/reference/python/)             | A FastAPI, Django, or Flask app, a Python service or machine, and a Python API.                                                         |
| [`github.com/masksrb/masks/go`](/reference/go/)  | A Go web app, service, or machine, and a Go API.                                                                                        |

The `masks` gem holds both Ruby SDKs. `Masks::Rails` loads only when Rails does.

The terms in this table mean:

|                           |                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Code flow and PKCE        | The browser signs in at masks and comes back to the app with a one-time code. The app trades the code for tokens. PKCE (Proof Key for Code Exchange) lets only the app that asked trade the code. |
| Handshake                 | The way an app registers itself with masks. See [connecting an app](#connecting-an-app).                                                                                                          |
| Initial access token      | A one-time token from masks that lets an app or a machine register itself as a client.                                                                                                            |
| Token exchange            | Trading one token for another. See [exchanging a token](#exchanging-a-token).                                                                                                                     |
| Client credentials        | A client asking for a token as itself, with nobody signed in.                                                                                                                                     |
| Revocation                | Telling masks to end a token.                                                                                                                                                                     |
| Introspection             | Asking masks whether a token is active.                                                                                                                                                           |
| Device flow               | A device with no browser shows a code. A person approves it on another device.                                                                                                                    |
| `private_key_jwt`         | A client proves who it is with a message signed by its private key. It sends no secret.                                                                                                           |
| DPoP                      | Ties a token to a key. Each request carries a proof signed by that key, so a copied token does not work without the key.                                                                          |
| Store of seen DPoP proofs | An API refuses a proof it has seen before. Without a shared store, each process of the API remembers only the proofs it has seen itself.                                                          |

## Connecting an app

1. Install the SDK. For Rails, run `bin/rails generate masks:install`.
2. Set the issuer. This is the address masks answers at, such as `https://acme.auth.example.com`.
3. Set the app's resource identifier. This is the app's own address, such as
   `https://app.example.com`. The app's redirect URIs (the addresses masks sends the browser back
   to) must share its origin: the same scheme, host, and port.
4. Open the handshake. The browser goes to masks' approval screen.
5. Approve it as a person holding `masks:manage` or `masks:handshake`. masks sends the browser back
   to the app with a one-time initial access token.
6. The app redeems the token with masks, server to server, and receives its client ID and secret.
   The secret never passes through the browser.

The app is then an approved [client](/guides/features/#registering-a-client). It signs people in
with the SDK's login URL, and its API checks access tokens with the SDK's verifier.

### Handshake parameters

The SDK sends these in the query of the handshake URL. Every address must share the resource's
origin.

|                              |                                                                                                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client_name`                | The name the approval screen shows.                                                                                                                   |
| `resource`                   | The app's resource identifier. Required.                                                                                                              |
| `scope`                      | The scopes the app asks for, separated by spaces. Required.                                                                                           |
| `redirect_uris`              | Where masks sends the browser after a sign-in. Repeat it for each address. Required.                                                                  |
| `return_to`                  | Where masks sends the browser with the initial access token. Required.                                                                                |
| `state`                      | A value masks hands back unchanged to `return_to`.                                                                                                    |
| `token_endpoint_auth_method` | How the app authenticates. The default is `client_secret_basic`.                                                                                      |
| `backchannel_logout_uri`     | Optional. Where masks posts a logout token when it ends a session.                                                                                    |
| `post_logout_redirect_uri`   | Optional. Where masks sends the browser after the person signs out of masks. Without it, a sign-out at masks cannot send the browser back to the app. |

### A single-page app

A single-page app with no backend runs the code flow in the page with `@masks/client`, as a public
client that keeps its tokens in `sessionStorage`. See [static sites](/reference/javascript/static/).

An app with a backend keeps the tokens on the backend, and the page holds only a cookie.
`@masks/client`'s session mode talks to that backend, which runs `Masks::Rails`, `@masks/server`,
the Python SDK, or the Go SDK.

## Delegation

A **delegation** lets an app act as one person at a provider while nobody is signed in. For example,
an app can sync a person's Google Drive at night, or call their Notion MCP server.

- masks stores and refreshes the provider's tokens.
- The app gets a token for one person's account, after that person consented to that app.
- The app calls the provider directly. It comes back to masks only when its token expires.

Each person sees every app using each of their accounts on their account page. They can stop any of
them there.

The [JavaScript](/reference/javascript/), [Python](/reference/python/), and [Go](/reference/go/)
guides show their SDK's delegation helpers. This section shows the requests underneath, and the
Ruby calls.

### Set up the provider

In `/manage`, on the provider's **Clients** tab:

1. Switch on **Let clients use an actor's Google account**. The label names the provider.
2. Fill in **What clients may do** with the provider's scopes beyond sign-in.
3. Fill in **Extra parameters when connecting** if the provider needs them for a refresh token.

| Provider      | What clients may do                              | Extra parameters                     |
| ------------- | ------------------------------------------------ | ------------------------------------ |
| Google        | `https://www.googleapis.com/auth/drive.readonly` | `access_type=offline prompt=consent` |
| Microsoft     | `offline_access Files.Read.All`                  |                                      |
| An MCP server | Leave it empty for whatever the server grants.   |                                      |

An MCP server always allows delegation, so it has no switch. Delegation uses the provider's
sign-in redirect URI, `/login/provider/<key>/callback`.

Changing **What clients may do** asks everybody to connect again the next time an app sends them
to `/authorize`.

### Let the app ask

Only an approved client can receive a delegation. Besides `openid` and `offline_access`, it needs:

|                  |                                                                                              |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `allowed_scopes` | `masks:delegate:` (every provider) or `masks:delegate:google` (one)                          |
| `grant_types`    | `authorization_code`, `refresh_token`, and `urn:ietf:params:oauth:grant-type:token-exchange` |

A handshake that asks for a `masks:delegate:` scope sets the grant types. With `Masks::Rails`, set:

```ruby
config.delegates = true
config.delegation_redirect_uri = ->(request) { "#{request.base_url}/connect/callback" }
```

`Masks::Rails` adds the scope and the redirect URI to its handshake. Your app answers the redirect
URI itself, as in [from Ruby](#from-ruby).

### Connect an account

1. Send the browser to `/authorize`. Keep `state` and the PKCE verifier in the session.

   ```
   GET https://auth.example.com/authorize
     ?response_type=code
     &client_id=CLIENT_ID
     &redirect_uri=https://app.example.com/connect/callback
     &scope=openid offline_access masks:delegate:google
     &state=STATE
     &code_challenge=CHALLENGE
     &code_challenge_method=S256
   ```

2. masks signs the person in and asks for consent. If it holds no usable token, it sends them to
   Google. Then it redirects back:

   ```
   GET https://app.example.com/connect/callback?code=CODE&state=STATE
   ```

3. Check `state`, then redeem the code as the client:

   ```
   POST https://auth.example.com/token
   Authorization: Basic base64(CLIENT_ID:CLIENT_SECRET)
   Content-Type: application/x-www-form-urlencoded

   grant_type=authorization_code
   &code=CODE
   &redirect_uri=https://app.example.com/connect/callback
   &code_verifier=VERIFIER
   ```

   ```json
   {
     "access_token": "eyJ…",
     "refresh_token": "Xk2…",
     "delegations": [
       {
         "connection": "3f1c9a0e-…",
         "provider": "google",
         "provider_name": "Google",
         "label": "ada@example.com",
         "subject": "8f4c…"
       }
     ]
   }
   ```

4. Store `delegations[].connection` (the account) and `refresh_token` (the secret), encrypted.

`subject` is the same `sub` your sign-in receives. Use it to refuse a connection that someone other
than the person who started it finished.

| `error`                | Means                                                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `access_denied`        | The person declined, took more than 15 minutes, or chose a provider account that is not theirs in masks. The provider refused, or is no longer available. |
| `login_required`       | A first connection to a provider that also signs people in needs a sign-in within the last 15 minutes. Send them again with `prompt=login`.               |
| `interaction_required` | You sent `prompt=none`, and masks has to ask something.                                                                                                   |
| `unauthorized_client`  | The client is not approved.                                                                                                                               |
| `invalid_scope`        | No provider with that key allows delegation.                                                                                                              |

### Get a provider token

Follow these steps when you have no provider token, or when it is about to expire.

1. Refresh the secret. Send no `scope`.

   ```
   POST https://auth.example.com/token
   Authorization: Basic base64(CLIENT_ID:CLIENT_SECRET)

   grant_type=refresh_token
   &refresh_token=SECRET
   ```

   ```json
   { "access_token": "eyJ…", "refresh_token": "NEW_SECRET", "expires_in": 3600 }
   ```

   Save `NEW_SECRET` first. The old one is spent.

2. Exchange the masks access token for the provider's:

   ```
   POST https://auth.example.com/token
   Authorization: Basic base64(CLIENT_ID:CLIENT_SECRET)

   grant_type=urn:ietf:params:oauth:grant-type:token-exchange
   &subject_token=eyJ…
   &subject_token_type=urn:ietf:params:oauth:token-type:access_token
   &requested_token_type=urn:masks:params:oauth:token-type:upstream_access_token
   &audience=3f1c9a0e-…
   ```

   ```json
   {
     "access_token": "ya29.…",
     "issued_token_type": "urn:masks:params:oauth:token-type:upstream_access_token",
     "token_type": "Bearer",
     "expires_in": 3542,
     "scope": "https://www.googleapis.com/auth/drive.readonly"
   }
   ```

Call Google with `ya29.…` until the time in `expires_in` has passed. On a 401, discard the token and
repeat these steps.

| Response                      | Means                                                                                                                 | Do                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `400 invalid_grant`           | The person stopped the app or disconnected, or the provider refused.                                                  | Ask them to connect again.     |
| `400 insufficient_scope`      | The token lacks `masks:delegate:<provider>`. A refresh that sent a narrower `scope` drops it from every later secret. | Ask them to connect again.     |
| `503 temporarily_unavailable` | The provider did not respond.                                                                                         | Retry later. Nothing was lost. |

### Rules for the secret

1. Keep every new secret. Each refresh replaces it, even when the exchange after it fails.
2. Refresh each secret from one place at a time. Using a secret twice revokes every secret in its
   family, the newest one included, and the person has to connect again. Lock around the refresh if
   more than one worker can reach it.
3. Use it within the client's refresh token lifetime, 30 days by default. Each refresh starts that
   time again.

### MCP servers

An MCP server that is its own OAuth server, such as `https://mcp.notion.com/mcp`, is a provider with
the protocol `mcp`. Given its URL, masks finds its authorization server and registers itself there.
The server must offer PKCE with S256 and a registration endpoint.

To call the MCP server:

1. Connect an account, as in [connect an account](#connect-an-account).
2. Get a token, as in [get a provider token](#get-a-provider-token).
3. Send the token to the MCP server as `Authorization: Bearer`.

### From Ruby

```ruby
delegations = Masks::Client.delegations(issuer, client_id:, client_secret:, redirect_uri:)

started = delegations.start(provider: "google")
session[:connecting] = started
redirect_to started["url"]

held = delegations.finish(params: params, started: session.delete(:connecting))
save(held.connection, held.secret)

upstream = delegations.token(secret, connection: connection)
save(connection, upstream.secret)
upstream.access_token
```

- `token` refreshes and exchanges in one call. `upstream.secret` replaces the secret passed in.
- `Delegations::Refused` means the person has to connect again.
- Retry after `Delegations::Unavailable`.
- Both errors carry `secret` when masks had already rotated it.

`Delegations::Fake` stands in for masks in tests. See [Masks::Client](/reference/ruby/client/).

## Calling a provider while the person is present

An app that calls a provider only while the person uses it can run its own OAuth flow there. The
`identities` scope adds the person's connected accounts to the claims, with an email address only
when it is confirmed. The flow is then a redirect with a hint:

```json
{
  "sub": "8f4c…",
  "identities": [
    {
      "provider": "google",
      "protocol": "oidc",
      "sub": "10769150350006150715",
      "email": "ada@gmail.com"
    }
  ]
}
```

```
https://accounts.google.com/o/oauth2/v2/auth?…&login_hint=ada@gmail.com
```

A [pairwise](/guides/features/#subject-identifiers) client never receives `identities`. A pairwise
client sees a different subject for each person than every other client does. An upstream subject is
the same for every client, so it would undo that separation.

## Exchanging a token

A token exchange ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)) trades one token for another
at `/token`. For example:

- a gateway gives a downstream service a token for that service only
- an agent holds a token recording that it acts for a person
- a backend trades its frontend's ID token for an access token of its own

The client must be registered for `urn:ietf:params:oauth:grant-type:token-exchange`.

```sh
curl -u "$CLIENT_ID:$CLIENT_SECRET" https://auth.example.com/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d subject_token="$ACCESS_TOKEN" \
  -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d scope="catalog:read" \
  -d resource=https://search.example.com
```

Each SDK sends the same request:

| SDK             | Call                              |
| --------------- | --------------------------------- |
| Ruby            | `Masks::Client::Session#exchange` |
| `@masks/server` | `client.exchange`                 |
| Python          | `client.exchange`                 |
| Go              | `Client.Exchange`                 |

A client that holds its tokens to a DPoP key proves it on the exchange too.

### What can be exchanged

| `subject_token_type`                                                  | At most                                                                | Expires no later than | Refused when                                                                 |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------- | ---------------------------------------------------------------------------- |
| `…:access_token`                                                      | The subject token's scopes and resources, and the client's own scopes. | The subject token.    | It is not live, or another issuer signed it.                                 |
| `…:id_token`                                                          | What the person consented to for this client.                          | The ID token.         | Its session ended, it was issued to another client, or the client is public. |
| `urn:masks:params:oauth:token-type:upstream_access_token` (requested) | See [delegation](#delegation).                                         |                       |                                                                              |

An exchange only narrows a token. `scope`, `resource`, and `requested_lifetime` can only ask for
less. Revoking the subject token revokes everything exchanged from it.

### Who is acting

A token exchanged from an access token has an `act` claim naming its holder. When a token is
exchanged again, the earlier `act` is nested inside the new one, so every holder stays listed:

```json
{
  "sub": "8b1f…",
  "client_id": "search-service",
  "act": { "sub": "search-service", "act": { "sub": "gateway" } }
}
```

A client acting as a more specific party sends that party's token as `actor_token`, with
`actor_token_type`. The actor token must be live and issued to this client.

An agent that [signs in as itself](/guides/features/#signing-in-as-itself) and acts for a person
sends:

- its own token as the actor
- the person's token as the subject

A client exchanging its own ID token acts for itself. The new token has no `act` unless an actor
token was sent.

masks does not exchange refresh tokens, SAML assertions, or other issuers' tokens. It does not read
`may_act`.

## Without an SDK

masks is a standard OpenID Connect provider. An app in a language with no SDK signs people in with
its usual library, using the code flow with PKCE.

### Registering the app

1. In `/manage`, open **Clients** and choose **Add client**.
2. Choose **Signs actors in**.
3. Name the app.
4. Enter its redirect URI.
5. Copy the client secret. masks shows it only once. The `client_id` stays on the client's page.

The app also needs:

- the issuer, which is the address masks answers at, such as `https://auth.example.com`
- discovery, which is at `/.well-known/openid-configuration` under the issuer

Ask for `groups` as well to receive the [groups claim](/guides/features/#groups).

A service with nobody signed in is a client that **Signs in as itself**. It holds no redirect URI.
It asks for its own token with client credentials.

### Checking access tokens

An access token from masks is a JWT (JSON Web Token) of type `at+jwt`. masks signs it with a key
published at `/.well-known/jwks.json`. An API checks:

- its signature
- its issuer
- that `aud` names the API

An app asks for a token for the API by sending `resource=https://api.example.com` when it signs in.
The token's `scope` holds the granted scopes, separated by spaces.

Each SDK's verifier makes all of those checks. It also checks the proof that comes with a DPoP-bound
token. The proof must be:

- signed by the token's key
- made for this method and URL
- made within the last 90 seconds, which allows for clocks that differ
- not seen before

A proof names the URL the client used. Behind a proxy, give the verifier the API's public URL:
`publicURL` in `@masks/server`, `public_url` in Python, `PublicURL` in Go, and `url:` on
`Masks::Client::Resource#authenticate` in Ruby. `Masks::Rails` uses the request's own URL, so it
depends on Rails trusting the proxy's headers.

In a language with no SDK, a JWT library checks a plain bearer token, a token that works for anyone
who holds it. With [jose](https://github.com/panva/jose):

```js
import { createRemoteJWKSet, jwtVerify } from "jose";

const keys = createRemoteJWKSet(
  new URL("https://auth.example.com/.well-known/jwks.json"),
);

const { payload } = await jwtVerify(token, keys, {
  issuer: "https://auth.example.com",
  audience: "https://api.example.com",
  typ: "at+jwt",
});
```

:::caution
That check alone accepts a DPoP-bound token without its proof. An API that receives DPoP-bound
tokens uses an SDK's verifier.
:::
