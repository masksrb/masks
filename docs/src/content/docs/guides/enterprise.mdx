Companies that buy an identity provider ask the same questions. Who did what?
Can a risky sign-in be stopped? Can our domain and our directory sit in front of
it? Can we show an auditor? This page lists each capability, what masks does
today, and how the rest will be built.

Each capability reuses what is already built. Event streaming supplies retried
delivery to shared signals. Sign-in policies supply the decision point for
step-up and adaptive risk. Tenants supply the isolation that organizations and
custom domains build on.

## Built

### Audit log

Every sign-in, consent, administrative change, token revocation, and key
rotation is an event. An event names the action, the account it happened to,
the account that did it, the client, the device, the IP address, and the user
agent. Events are read-only, belong to one tenant, and are deleted after 180
days by default. Manage lists them and filters by account, action, and client, and marks
the actions that call for attention, such as a refused sign-in or a replayed
refresh token.

### Event streaming

An event stream posts each event to an HTTPS endpoint as it happens, signed with
a secret that only the tenant and the receiver hold. Failed deliveries are
retried, and an address that resolves to a private network is refused. See
[Event streams](/guides/event-streams/) for the steps and the signature format.

### Single sign-on and provisioning

Masks signs people in through OpenID Connect, OAuth 2.0, and SAML 2.0
providers, acts as a SAML identity provider for applications, and keeps its
accounts in step with a directory over SCIM. See
[Features](/guides/features/) and [SSO and SAML](/guides/sso-saml/).

### Step-up authentication

Some actions need a stronger or fresher sign-in than the session holds, such as
moving money or reading a record.

- ID tokens carry `auth_time`, `amr`, and an `acr` of `urn:masks:acr:pwd` or
  `urn:masks:acr:mfa`.
- A client asks for a fresh sign-in with `max_age` or `prompt=login`.
- A client asks for a second factor with `acr_values=urn:masks:acr:mfa` or with
  an essential `acr` in the `claims` parameter. A session that already used a
  second factor is not asked again. Otherwise masks prompts for a factor the
  account holds, or asks the account to add one.
- The ID token reports the `acr` the sign-in reached.
- A sign-in policy can ask for a second factor at every app sign-in it covers.
  A session that started with a password alone is asked for one before the app
  receives a code. Requiring a second factor makes every account hold one, and
  lets a session that skipped it reach apps.

### Token exchange

A service acting for a person, including an AI agent, trades the token it holds
for a narrower one for a downstream service.

- Masks implements RFC 8693 token exchange. The subject is an access token or an
  ID token, an actor token adds to a nested `act` chain, and a provider's access
  token is released through a per-client
  [delegation](/guides/connecting-via-sdk/#delegation). See
  [exchanging a token](/guides/connecting-via-sdk/#exchanging-a-token).
- Each exchange is an event. A granted exchange records the scopes, the
  audience, and how many parties are in the `act` chain. A refused one records
  the error. Neither records the token.

Rich authorization requests (RFC 9396), which say in detail what the narrower
token may do, are planned.

### Session policies

A bank wants sessions that end after 15 minutes idle, and a consumer app wants
them to last a month. A sign-in policy sets a session lifetime and an idle
timeout. A session that runs past either ends, its refresh tokens stop working,
and an app covered by a stricter policy asks for the password again. See
[how long a session lasts](/guides/features/#how-long-a-session-lasts).

### Manage roles

An auditor reads without changing anything, a support team resets a factor
without touching signing keys, and a security team changes keys without
touching people. `masks:manage:read`, `masks:manage:support`, and
`masks:manage:security` sit beside `masks:manage`, and no role can grant a
role it does not hold. See [manage roles](/guides/security/#manage-roles).

### Organizations and roles

A business application has customers, and each customer has people in different
roles. An organization holds members in roles, and apps that ask for the
`organization` scope get the organization and the role in an `org` claim. Each
organization can have its own sign-in policy, its own provider that maps groups
to roles, its own SCIM directory, and its own event stream, and its owners
manage its members from their account page. See
[organizations](/guides/features/#organizations).

### Home-realm discovery

Someone types an email address, and masks sends them to their company's
provider. The tenant proves it controls the domain with a DNS record, and one
tenant cannot capture another company's domain. See
[sending a domain to its provider](/guides/sso-saml/#sending-a-domain-to-its-provider).

### Audit export and retention

A tenant keeps events for between 30 days and seven years, and any manager,
auditors included, downloads a range as a file. See
[keeping and exporting activity](/guides/security/#keeping-and-exporting-activity).

### Adaptive risk

A sign-in from a new device and network, a risky address range, or with a
breached password is riskier than one from a familiar device. masks scores
each sign-in, and a sign-in policy asks for a second factor or refuses from a
score it names. See [risky sign-ins](/guides/security/#risky-sign-ins).

### Passwordless email

A sign-in policy offers a six-digit code sent to the person's address as a
first factor, with or without a password. The form looks the same whether or
not the address has an account. See
[signing in with an emailed code](/guides/features/#signing-in-with-an-emailed-code).

### Shared signals

Other systems need to hear that a session ended or a credential changed without
waiting for a token to expire. Masks is an OpenID Shared Signals transmitter. A
receiver registers a stream, and masks pushes it signed CAEP and RISC events
about the people who use that receiver. See
[Shared signals](/guides/shared-signals/).

Accepting the same events from a provider, and ending the matching sessions, is
planned.

### Custom domains

A tenant serves sign-in from its own host, such as `login.example.com`, within a
domain it has proven with a DNS record. The host is a second issuer beside the
usual address, and a proxy such as Caddy issues its certificate on demand. See
[custom domains](/guides/self-hosting/#custom-domains).

Sending mail from the tenant's domain is planned.

## Planned

### Migration

Moving off another provider must not force everyone to reset a password.

- An import reads a file of accounts exported from Auth0 or Firebase, or a
  generic JSON file. Each password hash is kept in its original format, and
  masks replaces it with its own the first time the person signs in.
- Okta and Cognito do not export password hashes. For those, masks checks a
  password against the old provider the first time the person signs in, stores
  its own hash, and stops asking the old provider after that.
- Accounts arrive with their emails verified only when the export says so.
