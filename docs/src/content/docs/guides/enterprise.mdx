Companies that buy an identity provider ask the same questions. Who did what?
Can a risky sign-in be stopped? Can our domain and our directory sit in front of
it? Can we show an auditor? This page lists each capability, what masks does
today, and how the rest will be built.

Each planned capability reuses what is already built. Event streaming supplies
delivery and signing to shared signals. Sign-in policies supply the decision
point for step-up and adaptive risk. Tenants supply the isolation that
organizations and custom domains build on.

## Built

### Audit log

Every sign-in, consent, administrative change, token revocation, and key
rotation is an event. An event names the action, the account it happened to,
the account that did it, the client, the device, the IP address, and the user
agent. Events are read-only, belong to one tenant, and are deleted after 180
days. Manage lists them and filters by account, action, and client, and marks
the actions that call for attention, such as a refused sign-in or a replayed
refresh token.

### Event streaming

An event stream posts each event to an HTTPS endpoint as it happens, signed with
a secret that only the tenant and the receiver hold. Failed deliveries are
retried, and an address that resolves to a private network is refused. See
[Event streams](/guides/event-streams/) for the steps and the signature format.

### Single sign-on and provisioning

Masks signs people in through OpenID Connect, OAuth 2.0, and SAML 2.0
providers, acts as a SAML identity provider for applications, and keeps its
accounts in step with a directory over SCIM. See
[Features](/guides/features/) and [SSO and SAML](/guides/sso-saml/).

## Partly built

### Step-up authentication

Some actions need a stronger or fresher sign-in than the session holds, such as
moving money or reading a record.

Today:

- ID tokens carry `auth_time`, `amr`, and an `acr` of `urn:masks:acr:pwd` or
  `urn:masks:acr:mfa`.
- A client asks for a fresh sign-in with `max_age` or `prompt=login`.

Still to build:

- A client asks for a level with `acr_values`. Masks discovery already lists the
  two values, and the authorization endpoint does not act on the request yet.
- When the session falls short, masks asks for one more factor and issues a
  token that meets the request.
- A sign-in policy names the level a client requires, so the client does not
  have to ask on every request.

## Planned

### Organizations and roles

A business application has customers, and each customer has people in
different roles.

- An organization has members, invitations, and a role for each member.
- A token can be scoped to one organization and carries the member's role there.
- A sign-in policy can apply to one organization, so a customer can require a
  passkey without changing another customer's sign-in.
- Events record the organization, so one customer's log can be streamed to that
  customer.

### Custom domains

A tenant serves sign-in from its own domain, such as `login.example.com`.

- A tenant claims a domain and proves it with a DNS record.
- Masks issues a certificate for the domain and renews it.
- The issuer, links, and emails use the domain, and mail is sent from it once
  its DNS records are in place.

### Home-realm discovery

Someone types an email address, and masks sends them to their company's
provider.

- A provider claims one or more email domains.
- The sign-in form looks up the domain of the address and starts that provider's
  flow. An address with no claimed domain gets the normal form.
- Claiming a domain needs the same proof as a custom domain, so one tenant
  cannot capture another company's people.

### Adaptive risk

A sign-in from a new country, a known-bad address, or a breached password is
riskier than one from a remembered device.

- Each sign-in is scored from the device, the address, the time since the last
  sign-in, and a check of the password against known breaches.
- A sign-in policy maps a score to allowing the sign-in, asking for another
  factor, or refusing it.
- The score and the decision are recorded on the event.

### Shared signals

Other systems need to hear that a session ended or a credential was
compromised without waiting for a token to expire.

- Masks sends Shared Signals events (CAEP and RISC) to a receiver that registers
  a stream, reusing the delivery and signing of event streams.
- Masks accepts the same events from a provider and ends the matching sessions.

### Token exchange

A service acting for a person, including an AI agent, trades the token it holds
for a narrower one for a downstream service.

- Masks implements RFC 8693 token exchange, limited by the per-client
  [delegations](/guides/connecting-via-sdk/#delegation) it already records.
- Rich authorization requests (RFC 9396) say what the narrower token may do.
- Each exchange is an event.

### Migration

Moving off another provider must not force everyone to reset a password.

- An import reads exports from Auth0, Okta, Cognito, and Firebase.
- Each password hash is kept in its original format and rewritten with the masks
  hash the first time the person signs in.
- Accounts arrive with their emails verified only when the export says so.
