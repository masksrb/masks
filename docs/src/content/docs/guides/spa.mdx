---
title: Sign an SPA in
description: Two modes in one browser package — a session against a backend, or the code flow in the page.
---

`@masks/client` (`web/`) exists because the [engine](/guides/rails) answers every refusal with a
redirect, and a redirect answered to `fetch()` is either an opaque CORS failure or a login page
parsed as JSON.

```sh
npm install @masks/client
```

## Which mode

| Your app | Mode | Where the token lives |
| --- | --- | --- |
| an SPA in front of your own Rails app | BFF session | the server's encrypted session |
| a static site, or anything crossing an origin | browser PKCE | a closure in the page |

Prefer the first when it is available. Tokens that never reach JavaScript cannot be lifted by XSS,
and there is no refresh loop in the page.

## BFF session mode

Your Rails app mounts the [masks engine](/guides/rails) at `/auth`; the page asks it who is signed
in.

```ts
import { createSession } from "@masks/client";

const auth = createSession(); // defaults to basePath "/auth"

const account = await auth.session(); // Account, or null
if (!account) auth.login({ returnTo: "/dashboard" });
```

`SessionClient`:

| | |
| --- | --- |
| `session()` | the current account, or `null` |
| `status()` | the same question without throwing — `Status` |
| `require({ returnTo })` | an account, or a redirect to sign in |
| `login({ returnTo })` / `loginUrl({ returnTo })` | send the browser to masks |
| `handshake()` / `handshakeUrl()` | start [connecting this app](/guides/handshake) |
| `logout({ everywhere })` | drop the local session |

`SessionOptions` takes `basePath` (default `/auth`), `fetch`, and `csrfToken`. Requests carry
cookies (`credentials: "same-origin"`) and a CSRF token read from `<meta name="csrf-token">` unless
you pass one. Nothing here handles a JWT.

`status()` is what reports `handshake_required`, so the page can say what is wrong rather than
offering a sign-in button that goes nowhere:

```ts
const status = await auth.status()

if (status.state === 'handshake_required') {
  // status.handshakeUrl
}
```

## Browser PKCE mode

For an app with no backend of its own. The page runs the code flow itself.

```ts
import { createBrowserClient } from "@masks/client";

const client = createBrowserClient({
  issuer: "https://demo.auth.example",
  clientId: "2bb32482-…",
  redirectUri: `${location.origin}/callback`,
  scope: "openid profile email offline_access",
  resource: "https://demo.things.example/mcp",
});

await client.authorize({ returnTo: "/dashboard" });   // on a "sign in" click

if (client.pending()) {                                // on /callback
  const { returnTo } = await client.callback();
  location.replace(returnTo);
}

fetch("/api/things", { headers: { Authorization: client.authorization() } });
```

`BrowserClient`:

| | |
| --- | --- |
| `discover()` | the issuer's metadata, so no endpoint is written down |
| `authorize({ returnTo, prompt })` / `authorizeUrl(…)` | |
| `pending()` / `callback(url?)` | |
| `identity()` | the id token's claims |
| `tokens()` / `accessToken()` / `authorization()` | |
| `expired(leeway?)` / `refresh()` | |
| `logout()` | |

`scope` defaults to `openid profile email`. Both `scope` and `resource` accept a string or an array.

### Where the secrets sit

Tokens live in a closure and nowhere else. `localStorage` survives a tab close, is readable by every
script on the origin, and buys nothing a silent prompt cannot re-derive.

The PKCE verifier, `state`, `nonce` and `returnTo` must cross a redirect, so they persist under the
`masks:pending` key in `sessionStorage` (overridable with the `storage` option) — tab scoped,
cleared on callback, and useless without the single-use code they pair with. The pending record is
cleared even when `state` does not match, so a forged state cannot be retried against a live
verifier.

`S256` is computed with `crypto.subtle` — no dependency, no polyfill.

### The id token is verified in the page

`verifyIdToken` (`web/src/jwt.ts`) fetches the issuer's JWKS, imports the key named by `kid`, and
checks the signature, `iss`, `aud`, `nonce` and expiry with 60 seconds of leeway — all through
`crypto.subtle`. A token signed with an algorithm the client cannot verify is refused rather than
skipped.

### Telling it what to ask for

A PKCE client has to be told its `resource`; unlike the BFF it has no server config to read it from.
Get it wrong and you receive a token no resource server will accept — which is the
[audience restriction](/concepts/tokens) working.
