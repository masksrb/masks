`Masks::Rails` is a Rails engine inside the `masks` gem. It mounts the code flow into your
application, so signing in against a masks issuer is configuration rather than a controller you
write. It loads only when `Rails::Engine` is already defined; requiring the gem from a plain
Ruby process gets `Masks::Client` and nothing else.

```ruby
gem "masks"
```

## Install

```sh
bin/rails generate masks:install
```

That mounts the engine at `/auth`, writes `config/initializers/masks.rb`, and adds
`config/masks.json` to `.gitignore`. The initializer it writes:

```ruby
Masks::Rails.configure do |config|
  config.issuer = ENV.fetch("MASKS_ISSUER", "https://auth.example.com")

  # Uncomment when this app also accepts tokens of its own. `resource` is the
  # identifier tokens are minted for; `resource_scopes` are what it accepts.
  # config.resource = "https://app.example.com/api"
  # config.resource_scopes = []

  config.after_sign_in = "/"
  config.after_sign_out = "/"

  # config.credentials = ->(request) { Tenant.for(request).masks_credentials }
  # config.store = ->(request, registration) { Tenant.for(request).connect!(registration) }

  # config.sign_out_of_issuer = false
  # config.parent_controller = "ApplicationController"
end
```

Set `MASKS_ISSUER` to the tenant you're signing in against, such as
`https://acme.auth.example.com`, start the app, and open `/auth/handshake`.

## The handshake

A first-party app doesn't self-register anonymously, since that's also how a stranger's
connector would arrive. Opening `/auth/handshake` sends the browser to your masks server's
approval screen instead. Approve it there, and the one-time token that comes back is redeemed
server-side. The secret never travels through the browser and nobody types it anywhere.

The engine writes what comes back to `config/masks.json`, mode 600. A multi-tenant app wants a
row per tenant instead of a file per install, which is what `config.credentials` and
`config.store` are for:

```ruby
config.credentials = ->(request) { Tenant.for(request).masks_credentials }
config.store = ->(request, registration) { Tenant.for(request).connect!(registration) }
```

Those two lambdas are the whole integration for a multi-tenant app.

## Signing in

```ruby
class ApplicationController < ActionController::Base
  include Masks::Rails::Authentication

  before_action :authenticate_masks!
end
```

`authenticate_masks!` sends a signed-out visitor to `masks_login_url` and stops the request.
Once signed in, `masks_account` and `masks_claims` read the session, and `masks_identity` narrows
it to `sub`, `name`, `preferred_username`, `email`, `email_verified`, `tenant`, `picture`, and any
avatar claims. `masks_access_token` is the token to spend against a resource server.
`masks_disconnect!` tears the connection down and removes `config/masks.json`.

The full method list, generated from the engine's source, is in the
[Masks::Rails](/reference/rails/) reference.

## Accepting tokens

An app that is also a resource server, not just a consumer, checks bearers with
`Masks::Rails::ProtectedResource`:

```ruby
class ApiController < ActionController::Base
  include Masks::Rails::ProtectedResource
end
```

Set `config.resource` and `config.resource_scopes` in the initializer first. `resource` is the
identifier tokens are minted for and what `aud` is checked against; `resource_scopes` is what
this app accepts.

## Plain Ruby

Outside Rails, `Masks::Client` does discovery, PKCE, token exchange, and verification without
the engine. See [Masks::Client](/reference/ruby/) for the class and method reference, and the
[generated RDoc](/api/ruby/) for the fuller source-level docs.
