---
title: Self-hosting
description: Run the masks server in production.
---

masks ships as a container image. Point it at a Postgres server, and it migrates itself on boot.

```sh
docker pull ghcr.io/masksrb/masks:latest
```

## What it runs

masks is an OpenID Connect and OAuth 2.0 provider. It authenticates people, issues and verifies
tokens, and publishes each tenant's signing keys. It stores nothing about your application's data.

It runs as one container, with Puma in front of Rails. It needs one Postgres server, which holds
three databases named from `POSTGRES_DATABASE`: the primary, a cache, and a job queue. The only
file it keeps on local disk is the master key.

Background jobs, such as mail and retries, run in the web process by default.
`MASKS_JOBS_IN_WEB_SERVER=false` moves them to a second container running `bin/jobs`.

The web process also serves LDAP for apps that sign people in only over LDAP. See
[LDAP](/guides/ldap/).

## Image tags

| Tag | Pushed on | Platforms |
| --- | --- | --- |
| `:main` | every push to main | amd64 |
| `:sha-<commit>` | every push to main | amd64 |
| `:<version>`, such as `:0.3.0` | a server release | amd64, arm64 |
| `:latest` | a server release, moved to its version | amd64, arm64 |

Pin a version, and read
[CHANGELOG.md](https://github.com/masksrb/masks/blob/main/server/CHANGELOG.md) before moving to a
new one.

```yaml
image: ghcr.io/masksrb/masks:0.3.0
```

## Example `compose.yml`

```yaml
services:
  masks:
    image: ghcr.io/masksrb/masks:latest
    environment:
      POSTGRES_HOST: postgres
      POSTGRES_USER: masks
      POSTGRES_PASSWORD: ...
      POSTGRES_DATABASE: masks
      MASKS_MIGRATION_USER: masks_owner
      MASKS_MIGRATION_PASSWORD: ...
      MASKS_TENANTS: acme
      MASKS_PUBLIC_ORIGIN_TEMPLATE: https://%{subdomain}.auth.example.com
    volumes:
      - masks-storage:/rails/storage
    depends_on:
      - postgres
    logging:
      options:
        max-size: 10m
        max-file: "3"

  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ...
    volumes:
      - postgres:/var/lib/postgresql/data
      - ./initdb:/docker-entrypoint-initdb.d:ro

  caddy:
    image: caddy:2-alpine
    ports:
      - "443:443"
      - "80:80"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
    depends_on:
      - masks

volumes:
  postgres:
  masks-storage:
  caddy-data:
```

```
*.auth.example.com {
  reverse_proxy masks:3000
}
```

`initdb/01-roles.sql` creates the two roles masks connects as when the Postgres volume is first
initialized:

```sql
CREATE ROLE masks_owner WITH LOGIN PASSWORD '...' CREATEDB;
CREATE ROLE masks WITH LOGIN PASSWORD '...';
```

Every variable the server reads is in [ENV vars](/reference/environment/).

`/up` answers `up` while the server can reach its database, job queue, and cache, and `down` with a
503 when it cannot reach one of them. A health check on `/up` therefore also catches a stopped job
queue. The `logging` options cap each container's log, so a repeating fault cannot fill the disk.

`/up/jobs` answers `up` while every background job has succeeded for a day, and a 503 naming the
job classes that failed otherwise. Point a monitor at it, and leave it out of the container's health
check, since restarting the server does not fix a failing job. The errors themselves are in the logs.

## Database roles

masks keeps tenants apart with row-level security in Postgres. A superuser bypasses it, and the role
that owns a table can switch it off with one `ALTER TABLE`, so masks connects as two roles.

| Role | Variable | Holds |
| --- | --- | --- |
| `masks_owner` | `MASKS_MIGRATION_USER` | The databases and every table in them. `CREATEDB`, and nothing else. |
| `masks` | `POSTGRES_USER` | `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on the tables, and the sequences behind them. |

On every boot, the image's entrypoint runs `db:prepare` and `masks:grants` as the migration role,
then starts the server as the serving role. It refuses to start when `MASKS_MIGRATION_USER` is
unset or names the serving role, and the server refuses to answer a request while its role owns a
table that row-level security protects.

### Moving an existing database to two roles

A server that migrated and served as one role owns everything it created. Before you upgrade, run
this as a Postgres superuser in each of the three databases, such as `masks`, `masks_cache`, and
`masks_queue`:

```sql
CREATE ROLE masks_owner WITH LOGIN PASSWORD '...' CREATEDB;
REASSIGN OWNED BY masks TO masks_owner;
```

`CREATE ROLE` only needs to run once, because roles belong to the whole server. Then set
`MASKS_MIGRATION_USER` and `MASKS_MIGRATION_PASSWORD` and start the new image. Its first boot grants
`masks` the access it serves with.

## Encryption & secrets

For each tenant, the database holds accounts, sign-in factors, clients, tokens, signing keys, and
activity. Columns that hold secrets, such as signing keys, authenticator app secrets, provider and
sending service credentials, and connected accounts' tokens, are also encrypted with Active Record
Encryption (AES-256-GCM). Reading them requires the encryption keys as well as the database.

Four secrets protect this data. None of them appears in the compose file.

| Secret | Protects |
| --- | --- |
| `SECRET_KEY_BASE` | The session cookie. Anyone holding it can forge one. |
| `ENCRYPTION_PRIMARY_KEY` | The encrypted columns, through a key derived from it for each tenant. |
| `ENCRYPTION_DETERMINISTIC_KEY` | Nothing yet. Rails requires it. |
| `ENCRYPTION_KEY_DERIVATION_SALT` | The per-column keys derived from the two above. |

On first boot, the image's entrypoint generates a master key, writes it to
`/rails/storage/master.key`, and derives all four from it on every boot. Mount that path to a
volume, as above. A secret set as an environment variable takes precedence over the derived one.
See [ENV vars](/reference/environment/#required-in-production) for `MASKS_MASTER_KEY` and
`MASKS_MASTER_KEY_FILE`.

:::caution
Keep the master key with your database backups. Losing it makes every encrypted column unreadable,
permanently.
:::

### Per-tenant keys

Each tenant's encrypted columns use a key of that tenant's own. masks derives it from the primary
key and the tenant's UUID with HKDF-SHA256, so nothing new needs storing or backing up. A ciphertext
copied from one tenant's rows cannot be read in another tenant, and two tenants never share an
encryption key. Writing an encrypted column outside a tenant raises an error.

A database from an earlier version holds columns encrypted under the shared primary key. masks still
reads them. At boot, `bin/rails masks:tenants` looks for any column still under the shared key and,
if it finds one, re-encrypts every encrypted column under its tenant's key and prints that it is
done.

### Running more than one replica

Every replica needs the same master key. Set `MASKS_MASTER_KEY` on each, or mount one file at
`MASKS_MASTER_KEY_FILE` on all of them. A replica that generates its own key cannot read the
database's encrypted columns, and refuses to start with an error that says so. The same check stops
a server whose database was restored with a different key.

### Rotating the master key

1. Set `MASKS_PREVIOUS_MASTER_KEY` to the key in use now.
2. Put the new key in `MASKS_MASTER_KEY` or its file, and restart.
3. At boot, masks re-encrypts every encrypted column with keys derived from the new one and prints
   that it is done.
4. Remove `MASKS_PREVIOUS_MASTER_KEY` and restart again.

A new `SECRET_KEY_BASE` comes with the new key, so everyone signs in again after the restart.

## Metrics

Set `MASKS_METRICS_TOKEN` and point Prometheus at `/metrics` with that token as a bearer token:

```yaml
scrape_configs:
  - job_name: masks
    authorization:
      credentials: the-value-of-MASKS_METRICS_TOKEN
    static_configs:
      - targets: [masks:3000]
```

Each scrape counts from the database, so the figures agree across replicas. Every tenant reports its
accounts, live sessions, and the sign-ins, refused sign-ins, and access tokens of the last hour, under
a `tenant` label. The server also reports its tenants, the kinds of job that failed in the last day,
and the jobs waiting to run. Without the variable, `/metrics` answers 404.

## Backups, restores, and upgrades

Back up the primary database and the master key together. The primary holds every tenant's
accounts, clients, signing keys, and activity. The cache and queue databases hold rate limits,
replay records, and pending jobs, and can be recreated empty.

```sh
pg_dump --format=custom --file=masks.dump masks_production
```

Keep `master.key`, or the value of `MASKS_MASTER_KEY`, beside the dump. A dump restored without its
key cannot be read, and the server refuses to start.

To restore, stop the server, create the database as the migration role, and load the dump as it, so
the migration role owns every table again:

```sh
createdb --username=masks_owner masks_production
pg_restore --username=masks_owner --dbname=masks_production --no-owner masks.dump
```

Start the server with the same master key. Its first boot creates the cache and queue databases and
grants the serving role what it needs. Everyone keeps their passkeys and second factors, and sessions
that were live at the time of the dump work again.

To upgrade, pull the new image and restart. Each boot runs the migrations that have not run yet, so
skipping versions is fine. Read the release notes for anything that needs a step of your own, and take
a backup first, since migrations do not run backwards. With more than one replica, start one on the
new image, wait for `/up`, and then replace the rest.

## Multi-tenancy

A tenant is a separate set of accounts, clients, and signing keys at its own subdomain. The
compose file above declares Multi tenancy. Replace its `MASKS_TENANTS` line to change the mode.

| Mode | In `masks:`'s `environment:` | An unseen hostname |
| --- | --- | --- |
| Single | `MASKS_TENANT: acme` | Served by that one tenant. |
| Multi | `MASKS_TENANTS: acme,demo` | 404. |
| Dynamic | Neither (remove the line) | Claims a new tenant, since the template has `%{subdomain}`. |

See [declaring tenants](/guides/core-concepts/#declaring-tenants) for how each mode works.
`MASKS_SETUP_TOKEN` sets one setup token for every tenant. See
[setting a tenant up](/guides/core-concepts/#setting-a-tenant-up).

## Custom domains

A tenant can also serve sign-in from a host of its own, such as `login.example.com`.

1. In `/manage`, open **Settings → General → Domains**, claim `example.com`, and publish the TXT record it
   shows. masks checks the record every hour.
2. Point `login.example.com` at the server with a CNAME or an address record.
3. Under **Serve sign-in from your domain**, enter the host and choose **Serve**. Only an owner
   can, and the host must be within a domain the tenant has proven.

The tenant answers at both its usual address and the host. Each is a separate issuer, so an app
names the one it uses. A passkey works only on the address it was made on. When the proof lapses or
the domain is released, masks stops serving the host.

Caddy can issue each host a certificate on demand. Before issuing one, it asks
`/tls/allowed?domain=`, which answers 200 only for a host a tenant serves.

```
{
  on_demand_tls {
    ask http://masks:3000/tls/allowed
  }
}

*.auth.example.com {
  reverse_proxy masks:3000
}

https:// {
  tls {
    on_demand
  }
  reverse_proxy masks:3000
}
```

## Declaring apps in a file

A rebuilt server comes back the same way when its apps and groups live in a file. Mount one and name
it in `MASKS_CONFIG`, and every boot applies it:

```yaml
name: Home
accent_color: "#3355aa"

groups:
  admins:
    name: Admins
    members: [ada]

apps:
  grafana:
    preset: grafana
    url: https://grafana.example.com
    client_secret_env: GRAFANA_CLIENT_SECRET
    allowed_groups: [admins]
  dash:
    preset: proxy
    url: https://dash.example.com
  wiki:
    redirect_uris: [https://wiki.example.com/oauth/callback]
    scopes: [openid, profile, email, groups]
    refresh_token_lifetime: 604800
```

| | |
| --- | --- |
| An app's key | Its `client_id`, unless `client_id` names another, so the app's own settings never change. |
| `preset`, `url`, `slug` | A [known app](/guides/features/#adding-a-known-app), as **Add client** registers it. |
| `redirect_uris`, `scopes` | An app no preset covers. |
| `client_secret_env` | The variable that holds the app's secret. Without it, masks makes a secret the first time and prints it to the logs once. |
| `allowed_groups`, `access_token_lifetime`, `refresh_token_lifetime` | As on a client's page in `/manage`. |
| `groups` | Each group's name and the nicknames or emails of its members. A member must already have an account. |

Applying adds and updates, and never removes an app, a group, or a member the file no longer
names. A server with several tenants nests each one under `tenants:` by subdomain. A mistake stops
the boot with an error that names the app or group it is in.

## Getting back into a locked account

When nobody can sign in to reset an account, such as the only manager after losing their phone and
backup codes, name the account in `MASKS_RECOVER` and restart the server:

```yaml
    environment:
      MASKS_RECOVER: acme/owner
```

At boot, masks removes that account's authenticator app, backup codes, passkeys, and sign-in codes,
signs it out everywhere, and prints a link to the logs:

```
masks: acme: owner has no second factors now and every session is signed out. This link sets a new password once: https://acme.auth.example.com/reset/...
```

Open the link to choose a password, then sign in and set up a new second factor. A manager is asked
for one at that sign-in. Both steps appear in the account's activity. Remove `MASKS_RECOVER` and
restart again, since every boot repeats it. Without a tenant prefix, the account is found in every
tenant that has one by that nickname or email.

## System requirements

masks is a small Rails app with no fixed CPU or memory minimum. Two variables size it.

| Variable | Default | Sizes |
| --- | --- | --- |
| `RAILS_MAX_THREADS` | `3` | Puma's threads. When set, also the size of each database connection pool. |
| `JOB_CONCURRENCY` | `1` | The job supervisor's worker processes, with three threads each. |

Raise either if requests or jobs queue. See [Processes](/reference/environment/#processes).
