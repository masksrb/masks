title: Self-hosting
description: Run the masks server in production.
---

masks comes as a container image, a packaged copy of the server that Docker and similar tools run.
Point it at a Postgres server, and it migrates its databases each time it boots.

```sh
docker pull ghcr.io/masksrb/masks:latest
```

## What it runs

masks is an OpenID Connect and OAuth 2.0 provider. These are the standard protocols apps use to
sign people in and get tokens. masks:

- authenticates people
- issues and verifies tokens
- publishes each tenant's signing keys

It stores nothing about your application's data.

It runs as one container, with Puma in front of Rails. Puma is the web server that answers
requests. It needs one Postgres server, which holds three databases named from
`POSTGRES_DATABASE`:

- the primary
- a cache
- a job queue

The only file it keeps on local disk is the master key.

Background jobs, such as mail and retries, run in the web process by default. To move them to a
second container that runs `bin/jobs`, set `MASKS_JOBS_IN_WEB_SERVER=false`.

The web process also serves LDAP for apps that sign people in only over LDAP. See
[LDAP](/guides/ldap/).

## Image tags

| Tag | Pushed on | Platforms |
| --- | --- | --- |
| `:main` | Every push to main. | amd64 |
| `:sha-<commit>` | Every push to main. | amd64 |
| `:<version>`, such as `:0.3.0` | A server release. | amd64, arm64 |
| `:latest` | A server release. Moved to that release's version. | amd64, arm64 |

Pin a version. Read
[CHANGELOG.md](https://github.com/masksrb/masks/blob/main/server/CHANGELOG.md) before you move to a
new one.

```yaml
image: ghcr.io/masksrb/masks:0.3.0
```

## Example `compose.yml`

This file runs masks, Postgres, and Caddy. Caddy is a web server that gets TLS certificates and
passes each request on to masks.

```yaml
services:
  masks:
    image: ghcr.io/masksrb/masks:latest
    environment:
      POSTGRES_HOST: postgres
      POSTGRES_USER: masks
      POSTGRES_PASSWORD: ...
      POSTGRES_DATABASE: masks
      MASKS_MIGRATION_USER: masks_owner
      MASKS_MIGRATION_PASSWORD: ...
      MASKS_TENANTS: acme
      MASKS_PUBLIC_ORIGIN_TEMPLATE: https://%{subdomain}.auth.example.com
    volumes:
      - masks-storage:/rails/storage
    depends_on:
      - postgres
    logging:
      options:
        max-size: 10m
        max-file: "3"

  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ...
    volumes:
      - postgres:/var/lib/postgresql/data
      - ./initdb:/docker-entrypoint-initdb.d:ro

  caddy:
    image: caddy:2-alpine
    ports:
      - "443:443"
      - "80:80"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
    depends_on:
      - masks

volumes:
  postgres:
  masks-storage:
  caddy-data:
```

The `Caddyfile`:

```
*.auth.example.com {
  reverse_proxy masks:3000
}
```

`initdb/01-roles.sql` creates the two roles masks connects as. It runs when the Postgres volume is
first set up.

```sql
CREATE ROLE masks_owner WITH LOGIN PASSWORD '...' CREATEDB;
CREATE ROLE masks WITH LOGIN PASSWORD '...';
```

Every variable the server reads is in [ENV vars](/reference/environment/).

The `logging` options cap each container's log, so a repeating fault cannot fill the disk.

### Health checks

masks has two status pages. A health check is a request that a container runtime or a monitor makes
again and again to see if a service works.

| Path | Answers |
| --- | --- |
| `/up` | `up` while the server can reach its database, job queue, and cache. `down` with a 503 when it cannot reach one of them. |
| `/up/jobs` | `up` while every background job has succeeded for a day. Otherwise a 503 that names the job classes that failed. |

- Use `/up` for the container's health check. It also catches a stopped job queue.
- Point a monitor at `/up/jobs`. Leave it out of the container's health check, because restarting
  the server does not fix a failing job.
- The errors themselves are in the logs.

## Database roles

masks keeps tenants apart with row-level security in Postgres. Row-level security is a rule on
each table that limits which rows a role can see. Two kinds of role can get around it:

- A superuser bypasses it.
- The role that owns a table can switch it off with one `ALTER TABLE`.

So masks connects as two roles.

| Role | Variable | Holds |
| --- | --- | --- |
| `masks_owner` | `MASKS_MIGRATION_USER` | The databases and every table in them. `CREATEDB`, and nothing else. |
| `masks` | `POSTGRES_USER` | `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on the tables, and the sequences behind them. |

On every boot, the image's entrypoint:

1. Runs `db:prepare` and `masks:grants` as the migration role.
2. Starts the server as the serving role.

Two checks stop a server that is set up wrong:

- The entrypoint refuses to start when `MASKS_MIGRATION_USER` is unset or names the serving role.
- The server refuses to answer a request while its role owns a table that row-level security
  protects.

### Moving an existing database to two roles

A server that migrated and served as one role owns everything it created. To move it to two roles:

1. Before you upgrade, run this as a Postgres superuser in each of the three databases, such as
   `masks`, `masks_cache`, and `masks_queue`:

   ```sql
   CREATE ROLE masks_owner WITH LOGIN PASSWORD '...' CREATEDB;
   REASSIGN OWNED BY masks TO masks_owner;
   ```

   `CREATE ROLE` only needs to run once, because roles belong to the whole Postgres server.

2. Set `MASKS_MIGRATION_USER` and `MASKS_MIGRATION_PASSWORD`.
3. Start the new image.

Its first boot grants `masks` the access it serves with.

## Encryption and secrets

For each tenant, the database holds accounts, sign-in factors, clients, tokens, signing keys, and
activity.

Columns that hold secrets are also encrypted with Active Record Encryption (AES-256-GCM). To read
them, someone needs the encryption keys as well as the database. These columns include:

- signing keys
- authenticator app secrets
- provider credentials and sending service credentials
- connected accounts' tokens

Four secrets protect this data. None of them appears in the compose file.

| Secret | Protects |
| --- | --- |
| `SECRET_KEY_BASE` | The session cookie. Anyone holding it can forge one. |
| `ENCRYPTION_PRIMARY_KEY` | The encrypted columns, through a key derived from it for each tenant. |
| `ENCRYPTION_DETERMINISTIC_KEY` | Nothing yet. Rails requires it. |
| `ENCRYPTION_KEY_DERIVATION_SALT` | The per-column keys derived from the two above. |

On first boot, the image's entrypoint generates a master key and writes it to
`/rails/storage/master.key`. On every boot, it derives all four secrets from that key.

- Keep that path on a volume, as the [example](#example-composeyml) does.
- A secret set as an environment variable takes precedence over the derived one.
- See [ENV vars](/reference/environment/#required-in-production) for `MASKS_MASTER_KEY` and
  `MASKS_MASTER_KEY_FILE`.

:::caution
Keep the master key with your database backups. Losing it makes every encrypted column unreadable,
permanently.
:::

### Per-tenant keys

Each tenant's encrypted columns use a key of that tenant's own. masks derives it from the primary
key and the tenant's UUID with HKDF-SHA256, a standard way to make new keys from one key. Nothing
new needs storing or backing up.

- A ciphertext copied from one tenant's rows cannot be read in another tenant.
- Two tenants never share an encryption key.
- Writing an encrypted column outside a tenant raises an error.

A database from an earlier version holds columns encrypted under the shared primary key. masks still
reads them. At boot, `bin/rails masks:tenants` looks for any column still under the shared key. If
it finds one, it re-encrypts every encrypted column under its tenant's key and prints that it is
done.

### Running more than one replica

A replica is one of several copies of the server that share a database. Every replica needs the
same master key. Do one of these:

- Set `MASKS_MASTER_KEY` on each replica.
- Mount one file at `MASKS_MASTER_KEY_FILE` on all of them.

A replica that generates its own key cannot read the database's encrypted columns. It refuses to
start, with an error that says so. The same check stops a server whose database was restored with a
different key.

### Rotating the master key

1. Set `MASKS_PREVIOUS_MASTER_KEY` to the key in use now.
2. Put the new key in `MASKS_MASTER_KEY` or its file, and restart.
3. At boot, masks re-encrypts every encrypted column with keys derived from the new one and prints
   that it is done.
4. Remove `MASKS_PREVIOUS_MASTER_KEY` and restart again.

A new `SECRET_KEY_BASE` comes with the new key, so everyone signs in again after the restart.

## Metrics

masks can report figures to Prometheus, a tool that collects numbers from services over time.

1. Set `MASKS_METRICS_TOKEN`.
2. Point Prometheus at `/metrics`, with that token as a bearer token:

   ```yaml
   scrape_configs:
     - job_name: masks
       authorization:
         credentials: the-value-of-MASKS_METRICS_TOKEN
       static_configs:
         - targets: [masks:3000]
   ```

Without the variable, `/metrics` answers 404.

Each scrape counts from the database, so the figures agree across replicas.

Every tenant reports these under a `tenant` label:

- its accounts
- its live sessions
- its sign-ins, refused sign-ins, and access tokens from the last hour

The server also reports:

- its tenants
- the kinds of job that failed in the last day
- the jobs waiting to run

## Backups, restores, and upgrades

Back up the primary database and the master key together.

- The primary holds every tenant's accounts, clients, signing keys, and activity.
- The cache and queue databases hold rate limits, replay records, and pending jobs. They can be
  recreated empty.

### Back up

1. Dump the primary database:

   ```sh
   pg_dump --format=custom --file=masks.dump masks_production
   ```

2. Keep `master.key`, or the value of `MASKS_MASTER_KEY`, beside the dump.

A dump restored without its key cannot be read, and the server refuses to start.

### Restore

Restore as the migration role, so the migration role owns every table again.

1. Stop the server.
2. Create the database as the migration role, and load the dump as it:

   ```sh
   createdb --username=masks_owner masks_production
   pg_restore --username=masks_owner --dbname=masks_production --no-owner masks.dump
   ```

3. Start the server with the same master key.

Its first boot creates the cache and queue databases and grants the serving role what it needs.
Everyone keeps their passkeys and second factors. Sessions that were live at the time of the dump
work again.

### Upgrade

1. Take a backup. Migrations do not run backwards.
2. Read the release notes for anything that needs a step of your own.
3. Pull the new image and restart.

Each boot runs the migrations that have not run yet, so you can skip versions.

With more than one replica:

1. Start one replica on the new image.
2. Wait for `/up`.
3. Replace the rest.

## Multi-tenancy

A tenant is a separate set of accounts, clients, and signing keys at its own subdomain. The compose
file above declares Multi mode. To change the mode, replace its `MASKS_TENANTS` line.

| Mode | In `masks:`'s `environment:` | An unseen hostname |
| --- | --- | --- |
| Single | `MASKS_TENANT: acme` | Served by that one tenant. |
| Multi | `MASKS_TENANTS: acme,demo` | 404. |
| Dynamic | Neither (remove the line) | Claims a new tenant, since the template has `%{subdomain}`. |

- See [declaring tenants](/guides/core-concepts/#declaring-tenants) for how each mode works.
- `MASKS_SETUP_TOKEN` sets one setup token for every tenant. See
  [setting a tenant up](/guides/core-concepts/#setting-a-tenant-up).

## Custom domains

A tenant can also serve sign-in from a host of its own, such as `login.example.com`.

1. In `/manage`, open **Settings**, then the **General** tab, then **Domains**.
2. Claim `example.com`, and publish the TXT record it shows. masks checks the record every hour.
3. Point `login.example.com` at the server with a CNAME or an address record.
4. Under **Serve sign-in at**, enter the host and choose **Serve**. Only an owner can do this, and the
   host must be within a domain the tenant has proven.

What happens next:

- The tenant answers at both its usual address and the host.
- Each is a separate issuer, so an app names the one it uses.
- A passkey works only on the address it was made on.
- When the proof lapses or the domain is released, masks stops serving the host.

### Certificates on demand

Caddy can issue each host a certificate on demand. Before it issues one, it asks
`/tls/allowed?domain=`. That path answers 200 only for a host a tenant serves.

```
{
  on_demand_tls {
    ask http://masks:3000/tls/allowed
  }
}

*.auth.example.com {
  reverse_proxy masks:3000
}

https:// {
  tls {
    on_demand
  }
  reverse_proxy masks:3000
}
```

## Declaring apps in a file

When a server's apps and groups live in a file, a rebuilt server comes back the same way. Mount the
file and name it in `MASKS_CONFIG`. Every boot applies it.

```yaml
name: Home
accent_color: "#3355aa"

groups:
  admins:
    name: Admins
    members: [ada]

apps:
  grafana:
    preset: grafana
    url: https://grafana.example.com
    client_secret_env: GRAFANA_CLIENT_SECRET
    allowed_groups: [admins]
  dash:
    preset: proxy
    url: https://dash.example.com
  wiki:
    redirect_uris: [https://wiki.example.com/oauth/callback]
    scopes: [openid, profile, email, groups]
    refresh_token_lifetime: 604800
```

| | |
| --- | --- |
| An app's key | Its `client_id`, unless `client_id` names another. The app's own settings never have to change. |
| `preset`, `url`, `slug` | A [known product](/guides/features/#adding-a-known-app), as **Add client** registers it. |
| `redirect_uris`, `scopes` | An app no preset covers. |
| `client_secret_env` | The variable that holds the app's secret. Without it, masks makes a secret the first time and prints it to the logs once. |
| `allowed_groups`, `access_token_lifetime`, `refresh_token_lifetime` | As on a client's **Access** and **General** tabs in `/manage`. |
| `groups` | Each group's name. The nicknames or emails of its members. A member must already have an account. |

- Applying the file adds and updates. It never removes an app, a group, or a member the file no
  longer names.
- A server with several tenants nests each one under `tenants:` by subdomain.
- A mistake stops the boot with an error that names the app or group it is in.

## Getting back into a locked account

Use this when nobody can sign in to reset an account. For example, the only manager lost their phone
and backup codes.

1. Name the account in `MASKS_RECOVER`:

   ```yaml
       environment:
         MASKS_RECOVER: acme/owner
   ```

2. Restart the server. At boot, masks removes that account's authenticator app, backup codes,
   passkeys, and sign-in codes. It signs the account out everywhere and prints a link to the logs:

   ```
   masks: acme: owner has no second factors now and every session is signed out. This link sets a new password once: https://acme.auth.example.com/reset/...
   ```

3. Open the link and choose a password.
4. Sign in and set up a new second factor. masks asks a manager for one at that sign-in.
5. Remove `MASKS_RECOVER` and restart again. Every boot repeats the recovery while it is set.

Both the new password and the new second factor appear in the account's activity.

Without a tenant prefix, such as `owner` alone, masks finds the account in every tenant that has one
by that nickname or email.

## System requirements

masks is a small Rails app with no fixed CPU or memory minimum. Two variables size it.

| Variable | Default | Sizes |
| --- | --- | --- |
| `RAILS_MAX_THREADS` | `3` | Puma's threads. When set, also the size of each database connection pool. |
| `JOB_CONCURRENCY` | `1` | The job supervisor's worker processes, with three threads each. |

Raise either one if requests or jobs queue up. See [Processes](/reference/environment/#processes).
