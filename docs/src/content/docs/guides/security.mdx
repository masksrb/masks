## Tenant isolation

masks keeps each tenant's data apart with four layers.

| Layer | What it does | If it fails |
| --- | --- | --- |
| `TenantScoped` | Scopes every query in the app to the current tenant. | A forgotten scope would leak rows. |
| Row-level security | Postgres filters every row by tenant, with `FORCE ROW LEVEL SECURITY`. | masks refuses to run as a role that bypasses it. A production server also refuses a role that owns its tables. |
| Per-tenant signing keys | A token's `kid` (key ID) exists in one tenant's JWKS (its published list of public keys) only. | Verification refuses the token. |
| Per-tenant encryption keys | Each tenant's encrypted columns use a key derived from the primary key and the tenant's UUID. | A ciphertext moved into another tenant fails to decrypt. |

Some database roles get around row-level security:

- A `SUPERUSER` or `BYPASSRLS` role skips every policy, with no error.
- The role that owns a table can switch its policy off with one `ALTER TABLE`.

`Tenant.switch` checks the role once per process:

- It raises if the role holds either privilege.
- In a production server, it also raises if the role owns a table that row-level security protects.

So the server migrates as one role and serves as another. See
[database roles](/guides/self-hosting/#database-roles).

### Entering a tenant

masks enters a tenant before it runs any request or job.

1. A Rack middleware looks up the hostname and enters its tenant before any controller runs. A
   hostname with no tenant gets a 404 (Not Found) response.
2. Each job records the tenant it was enqueued in. The worker enters that tenant before it performs
   the job. A job enqueued outside a tenant raises. A maintenance job that works across every tenant
   must declare it:

   ```ruby
   class CleanupJob < ApplicationJob
     across_tenants!
   end
   ```

Other code that works across tenants uses `Tenant.switch(tenant) { ... }`. It sets a session-scoped
Postgres setting and opens no transaction.

Outside a tenant, every query returns zero rows. This includes `Model.unscoped`.

## Manage roles

Each manager holds one or more of four scopes. A scope is a named permission.

| Scope | Can |
| --- | --- |
| `masks:manage:read` | Read everything `/manage` shows. Change nothing. |
| `masks:manage:support` | Read. Help actors: sign them out, suspend and restore them, reset passwords and factors, and resend invitations. Revoke their sessions, consents, and tokens. |
| `masks:manage:security` | Read. Change signing keys, clients, providers, sign-in policies, sending services, and event streams. Change provisioning tokens for one organization. |
| `masks:manage` | Everything. This includes tenant settings, email templates, deleting actors, and granting any scope. |

How masks checks a role:

- A token for `/manage` carries the scopes the actor holds and `/manage` asked for.
- On every request, masks checks that the actor still holds those scopes.
- Every mutation declares the least scope it needs. A mutation that declares none needs
  `masks:manage`.
- `/manage` shows a line at the top of each page that says what a viewer below `masks:manage` can do.

### Limits on the narrower roles

A role below `masks:manage` has these limits:

- **It cannot change another manager.** This includes a session, token, consent, connection, or
  device that belongs to a manager. So support cannot change an owner's email address and then reset
  their password.
- **It cannot take over anyone's account.** Three actions need both `masks:manage:support` and
  `masks:manage:security`, or `masks:manage`:
  - changing an actor's email address
  - generating their backup codes
  - receiving a password reset link when masks cannot email the actor

  Support can still send a reset to the actor's own confirmed address. It can also reset second
  factors when the actor asks for help.
- **It cannot give out manage access.** It cannot give an actor or a client any manage scope or
  `masks:scim`. It cannot issue a provisioning token for every account. Either one would reach
  managers through SCIM, the protocol a directory uses to add and change accounts.
- **It cannot change a client that can carry a manage scope.** So it cannot point `/manage` at
  another address.
- **It cannot connect `/manage` in a new browser.** It can open `/manage` in a new browser once an
  owner has connected it.

Taking a role away ends it on the actor's next request. masks refuses their token, and `/manage`
asks them to sign in again.

## Rate limits

A rate limit counts attempts over a period of time. Once the count reaches the limit, masks answers
with an error.

- masks keeps each count per tenant.
- You set these limits with environment variables. See [ENV vars](/reference/environment/#rate-limits).

| Limit | Counted per | Covers |
| --- | --- | --- |
| `MASKS_ATTEMPT_LIMIT` | IP address | Passwords, codes, and passkeys at sign-in. Sign-in through a provider. |
| `MASKS_ACCOUNT_ATTEMPT_LIMIT` | Account | The same attempts against one account from any address. Password changes. Sign-in approvals. |
| `MASKS_RECOVERY_LIMIT` | IP address or account | Codes and links sent by email or SMS (text message). |
| `MASKS_REGISTRATION_LIMIT` | IP address | Dynamic client registration. |
| `MASKS_DEVICE_CODE_LIMIT` | IP address | User codes entered at `/device`. |
| `MASKS_CLAIM_LIMIT` | IP address, across tenants | Tenants claimed on first visit under a subdomain template. |
| `MASKS_CLAIM_CEILING` | The whole server | The same claims, from every address together. |

These limits are fixed:

| Endpoint | Limit |
| --- | --- |
| Token, pushed request, device authorization, and SAML sign-in | 60 per IP address each minute |
| Introspection | 120 per IP address each minute |
| SCIM | 600 per IP address each minute |
| Organization invitations | 30 per account each minute |
| Account download | 5 per account each hour |

## Risky sign-ins

masks can give each sign-in a risk score from 0 to 100. It does this when a sign-in policy sets a
score to act on. The score is worked out right after the first factor.

| Signal | Adds |
| --- | --- |
| A device the account has not signed in from in 90 days, or no device at all | 30 |
| A network the account has not signed in from in 90 days. For IPv4, a network is a /24: addresses that share the first three numbers. For IPv6, it is a /48. | 25 |
| An address in one of the tenant's **Risky networks** | 50 |
| Three or more refused attempts on the account in the last hour. Ten or more adds 40. | 20 |
| No sign-in for six months | 10 |
| A password found in a known breach | 40 |

An account with no sign-in in the last 90 days has nothing to compare. So the device and the network
add nothing.

To act on the score, use **Risk** in a sign-in policy:

- **Ask for a second factor at a score of** asks for a second factor from that score up. An account
  without one is asked to add one, as in [step-up](/guides/enterprise/#step-up-authentication).
- **Refuse at** stops the sign-in from that score up, and asks for the first factor again. It must
  be higher than the score that asks for a second factor.

What happens with any score above zero:

- masks records it as `sign_in.risky`, with the signals.
- The actor gets a security email.

The tenant's risky networks are under **Settings**, **Policies**, **Who may sign in**.

### Breached passwords

**Refuse passwords found in known breaches** checks passwords against the
[Pwned Passwords](https://haveibeenpwned.com/API/v3#PwnedPasswords) range API. It checks each new
password, and each password used to sign in.

The password never leaves the server:

1. masks takes the password's SHA-1 hash, a fixed-length code computed from the password.
2. It sends only the first five characters of the hash.
3. It compares the rest of the hash itself. The full hash never leaves the server either.

What masks does with the result:

- A new password that is breached is refused.
- A breached password used to sign in adds to the risk score.
- If the service does not answer within three seconds, masks allows the password.

## Security emails

masks emails an actor when something changes on their account.

| Group | Sent when |
| --- | --- |
| Password | The password is changed or reset. |
| Factors | A passkey, an authenticator app, backup codes, or email or SMS codes are added or removed. A backup code is spent. |
| Sessions | A new device signs in. A sign-in looks unusual and is asked for more or refused. A session is signed out. A device is blocked. |
| Apps and connected accounts | An app is allowed in. A connected account is connected or removed. A device sign-in is approved. |
| Account | A manager changes the actor's scopes. The actor downloads their account. |
| Organizations | Someone else changes the actor's role in an organization, or removes them. Someone archives an organization the actor is signed in to an app for. See [what members are told](/guides/organizations/#what-members-are-told). |

Rules for these emails:

- masks reports a new sign-in once per device.
- Emails go only to a confirmed address. An account with no confirmed address gets none, and the
  account page says so.
- An actor can turn any group off under **Emails we send you** on the account page.
- Each email names the device and the IP address the change came from, in the actor's time zone.

To preview every email masks sends, open **Messages**, **Templates** in `/manage`. Each preview uses
sample actors and the tenant's own name and links.

Each email is headed by a name and logo:

- An email sent while someone signs in to an approved app is headed by that app's logo and name.
- Every other email is headed by the tenant.
- An app nobody approved never heads an email. So a self-registered app cannot use the tenant's mail
  to pass as someone else.

### Editing an email template

An owner can edit these templates under **Messages**, **Templates** in `/manage`:

- invitation
- organization invitation
- password reset
- email confirmation
- confirmation code
- approval request
- approval

An owner can also add a signature that closes every email.

How the edits work:

- The subject (up to 150 characters) replaces the subject masks writes. So does the opening text (up
  to 2,000 characters). Leave either blank to keep masks' own.
- Both are plain text. Markup shows as written, and no link can be added. A blank line starts a new
  paragraph.
- `{{tenant}}`, `{{name}}`, `{{nickname}}`, `{{organization}}`, `{{role}}`, and `{{code}}` are
  placeholders. Each one fills in where the email has it. The page lists which placeholders each
  email offers. A placeholder an email does not offer is refused.
- masks still adds the button or the code, and how long it lasts. It also adds the lines that tell
  an actor what to do if it was not them. A password reset that a manager started still names the
  manager.
- A template applies in every language the tenant serves.
- masks records each change as `mail_template.updated`.

## Keeping and exporting activity

masks keeps each event for 180 days by default.

To change how long, the owner sets a period under **Settings**, **General**, **Activity**. It can be
from 30 days to seven years. A nightly job deletes older events, so a shorter period takes effect the
next night.

To download a copy:

1. Open **Activity**.
2. Choose a range of up to 366 days.
3. Choose **Download**.

About the file:

- It has one event per line, as JSON, in the same shape that
  [event streams](/guides/event-streams/#what-is-sent) send.
- It follows the filter on the page.
- Any manage role may download it. masks records each download as `events.exported`.
- The link lasts ten minutes. It works only in a browser signed in as the manager who asked for it.
- A range with more than 250,000 events is refused.

For a copy that keeps up to date on its own, use an [event stream](/guides/event-streams/).

## Calls to other servers

masks calls addresses that apps and managers supply. A bad address could make masks call a server
on a private network, so masks checks each one.

masks makes these calls:

- a client's `jwks_uri`, `sector_identifier_uri`, `logo_uri`, metadata document, back-channel logout
  URI, and shared signals endpoint
- a resource's protected resource metadata
- every provider's endpoints and SAML metadata
- each SMS service
- each event stream's endpoint
- the Pwned Passwords API

Each of these calls:

- uses `https`, with no username or password in the address
- looks up the hostname, and refuses it if any of its addresses is private, loopback, link-local, or
  reserved
- connects to the address it checked
- stops at a time limit and a size limit set for each kind of call

In development and test, masks allows `http` and private addresses.

Some apps and providers live on a private network, such as a tailnet (a private network across your
devices) or an identity provider inside the office. List their address ranges in
`MASKS_OUTBOUND_ALLOWED`, separated by commas. See [ENV vars](/reference/environment/).

:::caution
Every client that can register itself can make masks call a range in `MASKS_OUTBOUND_ALLOWED`. List
only the ranges you mean.
:::

## Rotating signing keys

masks stages a new key before it signs anything. Clients that cache the JWKS then fetch the key
before they see a token it signed. See [signing keys](/guides/core-concepts/#signing-keys) for the
states a key moves through.

| Action | Does | The outgoing key |
| --- | --- | --- |
| Stage | Publishes a new key ahead of time. One at a time. | Keeps signing. |
| Activate | Makes the staged key the signing key. | Verifies for 24 hours. |
| Rotate | Generates and activates a key at once. Use it when caches cannot wait. | Verifies for 24 hours. |
| Discard | Removes a staged key, which has signed nothing. | Keeps signing. |

- Only a staged key can be activated or discarded.
- SAML applications must read masks' metadata again after a rotation.

### Rotating on a schedule

Rotation is by hand until an owner picks a schedule. To pick one, open **Settings**, **General**,
**Signing keys**, and choose every 30, 90, 180, or 365 days.

A daily job then:

1. Stages the next key a day before the active key reaches that age.
2. Activates it a day after staging. So clients that cache the JWKS see it before it signs.

A key staged by hand is activated on the same schedule. The job records each step in the activity.

## Pushed requests

A normal authorization request puts every parameter in the address bar. There, browser history,
logs, and later pages can read it.

A pushed request ([RFC 9126](https://www.rfc-editor.org/rfc/rfc9126.html)) sends the parameters to
`/par` over the back channel, a direct call from the client's server to masks. Only a reference goes
in the URL. Discovery advertises `pushed_authorization_request_endpoint`.

1. Post the parameters to `/par`. Authenticate the same way as at `/token`. Include `client_id` in
   the body, even with Basic auth. A public client sends its `client_id` and no secret.

   ```sh
   curl -u "$CLIENT_ID:$CLIENT_SECRET" https://demo.auth.example.com/par \
     -d client_id="$CLIENT_ID" \
     -d response_type=code \
     -d redirect_uri=https://app.example.com/cb \
     -d scope="openid profile" \
     -d code_challenge="$CHALLENGE" \
     -d code_challenge_method=S256 \
     -d state="$STATE"
   ```

   ```json
   {
     "request_uri": "urn:ietf:params:oauth:request_uri:8mZ1...",
     "expires_in": 90
   }
   ```

2. Redirect to `/authorize` with only the client ID and the reference:

   ```
   https://demo.auth.example.com/authorize
     ?client_id=...
     &request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3A8mZ1...
   ```

The reference has these rules:

- It lasts 90 seconds.
- It works once.
- It works only for the client that pushed it.
- Following it twice, late, or with another `client_id` returns `invalid_request_uri`.
- A wrong `client_id` does not use it up.

### Requiring pushed requests

:::caution
Turn this on only after the client already pushes its requests.
:::

```graphql
mutation {
  updateClient(clientId: "...", requirePushedAuthorizationRequests: true) {
    client { clientId }
  }
}
```

After this:

- masks refuses a plain `/authorize` link for that client with `invalid_request`.
- Sign-in and consent continue the pushed request.

A self-registered client can ask for the same setting when it registers.

## Signed requests

A client with `jwks` or a `jwks_uri` can send the whole request as a signed JWT. A JWT is a JSON
token with a signature. This one is called a request object
([RFC 9101](https://www.rfc-editor.org/rfc/rfc9101.html)), and it holds the parameters as claims:

```json
{
  "iss": "$CLIENT_ID",
  "aud": "https://demo.auth.example.com",
  "client_id": "$CLIENT_ID",
  "exp": 1789000300,
  "nbf": 1789000000,
  "jti": "5c1f...",
  "response_type": "code",
  "redirect_uri": "https://app.example.com/cb",
  "scope": "openid profile",
  "code_challenge": "$CHALLENGE",
  "code_challenge_method": "S256",
  "state": "$STATE"
}
```

To send it:

1. Give the JWT the type `oauth-authz-req+jwt`.
2. Send it as `request`, next to `client_id`, to `/authorize` or `/par`.

| Claim or property | Rule |
| --- | --- |
| Signature | RSA, RSA-PSS, or ECDSA, with a registered key. `none` and shared secrets are refused. |
| `iss` | The client. |
| `aud` | This issuer. |
| `client_id` | The same as the `client_id` next to it. |
| `exp` | Required. At most an hour away. |
| `nbf` | Optional. Not in the future, and at most an hour ago. |
| `jti` | Optional. Used up on first use. |

More rules:

- A pushed request or a request object is the whole request. masks ignores anything else in the
  `/authorize` query.
- masks refuses a request object with `invalid_request_object` if it fails a rule, or if it holds
  its own `request` or `request_uri`.
- `requireSignedRequestObject` requires signing, in the same way that
  `requirePushedAuthorizationRequests` requires pushing.
- masks accepts only a `request_uri` it issued from `/par`. It never fetches one from a client URL.

## Binding a token with DPoP

A bearer token works for anyone who holds it. DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449))
binds a token to a key the client keeps. A copied token is then useless without the key. masks binds
a token for any client that asks.

1. The client generates a key pair and keeps it.
2. For each request, it signs a *proof*. A proof is a JWT typed `dpop+jwt` that names the method and
   URL, with the public key in its header.
3. It sends the proof in the `DPoP` header:

   ```
   POST /token HTTP/1.1
   DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2Iiwiandr...
   ```

4. masks returns a bound token:

   ```json
   { "access_token": "...", "token_type": "DPoP", "expires_in": 3600 }
   ```

The token's `cnf` claim holds `jkt`, the key's SHA-256 thumbprint
([RFC 7638](https://www.rfc-editor.org/rfc/rfc7638)). A thumbprint is a short hash that identifies
the key.

To use the token, the client:

- sends it with the `DPoP` scheme
- sends a new proof every time
- includes `ath`, the token's hash, in each proof sent with a token

```
GET /userinfo HTTP/1.1
Authorization: DPoP eyJhbGciOiJSUzI1NiIs...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs...
```

### What masks refuses

| Refused | Why |
| --- | --- |
| A bound token sent as `Bearer` | A bound token needs a proof. |
| A proof signed by another key | |
| A proof whose `htm` or `htu` names another request | |
| A proof with no `ath`, or the wrong one | |
| A proof older than 90 seconds, or more than 30 seconds in the future | A 60-second window, plus 30 seconds of leeway. |
| A proof with no `jti`, or one already seen | It is a replay. |
| A proof that holds a private key, a symmetric key, or `alg: none` | |
| Any algorithm except `ES256`, `ES384`, `ES512`, `PS256`, `PS384`, `PS512`, `RS256` | |

A refused proof returns:

- at a resource, `401` with `WWW-Authenticate: DPoP error="invalid_dpop_proof"` and the accepted
  `algs`
- at `/token`, `400 invalid_dpop_proof`

masks sends no nonce.

### Binding earlier

- **Authorization code.** `dpop_jkt` on `/authorize` binds the code to the key. So an intercepted
  code cannot be redeemed:

  ```
  GET /authorize?...&dpop_jkt=NzbLsXh8uDCcd-6MNwXF4W_7noWXFZAfHkxZsRGC9Xs
  ```

- **Refresh token.** A bound grant's refresh token is bound too. masks refuses a proof that does not
  match before it uses up the refresh token.

### Requiring a bound token

masks refuses a token without a proof to a client with `dpop_bound_access_tokens` set.

- A client sets it when it registers.
- A manager sets it with `dpopBoundAccessTokens` on `updateClient`.

```json
{ "client_name": "...", "dpop_bound_access_tokens": true }
```

## Rich authorization requests

A scope says what kind of thing an app may do. `authorization_details`
([RFC 9396](https://www.rfc-editor.org/rfc/rfc9396)) says exactly what. For example, one payment of
123.50 euros to one payee.

### Declaring a type

An approved client that serves these requests declares each type it accepts. It does this under
**Authorization details** on its **Endpoints** tab in `/manage`.

A declaration has:

- a label for the consent screen
- a schema
- optionally, `remember`

```json
{
  "payment_initiation": {
    "label": "Send a payment",
    "remember": 2592000,
    "schema": {
      "type": "object",
      "required": ["instructedAmount"],
      "properties": {
        "instructedAmount": {
          "type": "object",
          "required": ["currency", "amount"],
          "properties": {
            "currency": { "type": "string", "enum": ["EUR", "USD"] },
            "amount": { "type": "string", "maxLength": 20 }
          }
        },
        "creditorName": { "type": "string", "maxLength": 140 }
      }
    }
  }
}
```

- A schema can use `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`,
  `maxLength`, `maxItems`, `minimum`, `maximum`, `title`, and `description`.
- A field the schema does not list is refused, unless `additionalProperties` is `true`.
- `remember` is a number of seconds, up to 400 days. Without it, the consent screen asks about the
  type every time.
- Discovery lists every declared type in `authorization_details_types_supported`.

### Asking

The app that asks:

1. Registers the types it uses in `authorization_details_types`.
2. Sends the details as a JSON array to `/authorize` or `/par`, or in a signed request object.

```
GET /authorize?response_type=code&client_id=…&scope=openid
  &authorization_details=[{"type":"payment_initiation","instructedAmount":{"currency":"EUR","amount":"123.50"},"creditorName":"Merchant A"}]
```

masks refuses these with `invalid_authorization_details`:

- a type nobody declared
- a type the app did not register
- an entry its schema does not allow
- more than ten entries
- more than 8 kilobytes

`client_credentials` does not accept them.

### Consent

The consent screen lists each entry with its label and fields.

- It asks about every entry, even when the actor allowed the app before.
- It skips an entry only when the actor allowed it before and its type sets `remember`. masks keeps
  that allowed entry on the actor's consent for that long.
- If any entry in a request is not kept, the screen asks about all of them.
- An app that skips consent still asks about entries that are not kept.

Where kept entries show:

- The actor sees what is kept, and until when, under **Apps you have let in** on their account page.
- A manager sees it on the actor's and the app's consents in `/manage`.

masks forgets a kept entry when the app is revoked, or when the client's
[consent lifetime](/guides/features/#consent) ends.

### Tokens

- The granted details are in the token response, the access token's `authorization_details` claim,
  and introspection.
- At the token endpoint, the app can send `authorization_details` to narrow an access token to some
  of the granted entries.
- A refresh token keeps every granted entry.
- A [token exchange](/guides/connecting-via-sdk/#exchanging-a-token) passes them on or narrows them.
- Nothing can add an entry that was not granted.
