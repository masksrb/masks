---
title: Connect an app
description: How an application gets a client a person approved, without anyone copying a secret.
---

An application cannot sign anyone in until it holds a `client_id` and a secret. The handshake is how
it gets them: the app asks, a person approves at masks, and the credentials are minted afterwards and
fetched server to server. No secret travels through the browser.

`server/app/models/handshake.rb`, `server/app/controllers/handshakes_controller.rb`,
`client/lib/masks/client/handshake.rb`

## What happens

1. The app sends the browser to `GET /handshake` at its issuer, naming itself (`client_name`), the
   `resource` it serves, the `redirect_uris` it will use, the `scope` it wants, a `return_to` and a
   `state`.
2. masks signs the person in first if nobody has an account yet — first run is
   [a state at the head of the login machine](/concepts/login), not a wizard beside it — then shows
   what is being connected.
3. Approving creates the client, grants the approving actor those scopes, and mints a one-time
   **initial access token** (RFC 7591 §3.1), which travels back on the redirect.
4. The app redeems that token at `POST /register` with no browser involved. The secret comes back on
   that response.

`redirect_uris` is read off the raw query string as well as `params`, so a repeated parameter is not
collapsed to its last value.

The client that comes back is the one that was approved. The registration body cannot widen it — a
request naming other redirect URIs or broader scopes changes nothing, because approval created the
row rather than authorizing a later description of one.

Everything must share one origin: the resource, the redirect URIs, and where the browser is sent
back to. The approval screen names one place, so a crafted URL cannot get an app at one origin
approved and the token delivered to another.

A second handshake for the same resource **rotates** the client it finds rather than registering a
second one. The app picks up new credentials; the old secret stops working.

A handshake registers for `authorization_code` and `refresh_token` with
`client_secret_basic` (`Handshake::GRANT_TYPES`, `Handshake::AUTH_METHOD`).

## In a Rails app

The engine ships the whole consumer half. Tell it how to read and write credentials, and mount it:

```ruby
Masks::Rails.configure do |config|
  config.name = "things"
  config.issuer = ->(request) { "https://#{request.host.split('.').first}.auth.example" }
  config.resource = ->(request) { "https://#{request.host}/mcp" }
  config.credentials = ->(request) { Tenant.resolve(request.host)&.masks_credentials }
  config.store = ->(request, registration) { Tenant.resolve!(request.host).connect!(registration) }
end
```

| | |
| --- | --- |
| `credentials` | a hash of `client_id` and `client_secret`, or `nil` when there are none yet |
| `store` | given `(request, registration)` — the [`Registration`](/reference/configuration) the handshake redeemed, carrying `client_id`, `client_secret`, `access_token` and `uri` |
| `forget` | given `(request)`, to drop them again |

An app that sets `store` and not `forget` is never offered a disconnect (`Configuration#can_forget?`).
Set neither and the default is a JSON file at `config/masks.json`.

`/auth/handshake` renders a page with one button, `/auth/handshake/callback` redeems the token and
calls `store`, and until credentials exist every refusal says `handshake_required` rather than
sending a browser to a login that cannot work:

```json
{ "signed_in": false, "error": "handshake_required", "handshake_url": "/auth/handshake" }
```

An app that has already been connected will not offer the handshake again to a browser that is not
signed in.

`Configuration#issuer_speaks!` checks `masks_protocol_version` in discovery against
`MINIMUM_ISSUER`, so an issuer predating the handshake says so rather than failing at the one screen
that exists to be the first thing anybody touches.

## Without Rails

`Masks::Client::Handshake` reads `handshake_endpoint` out of discovery, so no application writes
another server's routes down.

```ruby
handshake = Masks::Client::Handshake.new(
  issuer,
  name: "things",
  resource: "https://jons.things.example/mcp",
  redirect_uris: [ "https://jons.things.example/auth/callback" ],
  return_to: "https://jons.things.example/connected",
  scope: %w[openid profile email offline_access things:read]
)

started = handshake.start          # => { url:, state: } — send the browser, hold the state
registration = handshake.complete(params, state: held)
```

`complete` refuses before it redeems anything:

| | |
| --- | --- |
| an `error` on the redirect | raised as it was given |
| a `state` that does not match | `invalid_state` |
| an `iss` from another issuer | `invalid_issuer` |
| no `initial_access_token` | `invalid_request` |

What it returns is a `Registration`, which builds a `Session` with `session(redirect_uri:)`.

## In the browser

`@masks/client` reports the same state to a single-page app:

```ts
const status = await session.status()

if (status.state === 'handshake_required') {
  // status.handshakeUrl
}
```
