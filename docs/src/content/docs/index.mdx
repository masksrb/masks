An auth server — a standalone, self-hostable OpenID Connect provider — and the two pieces an
application needs to sign in against it.

```
server/    the standalone OIDC provider     Rails, Postgres, per-tenant keys
client/    masks-client                     discovery, PKCE, exchange, verification
engine/    masks-rails                      the consumer half, mounted in a host app
```

## The server is not an engine, and the engine is not the server

An earlier version of masks shipped an engine *plus* a host app *plus* a gem, and the engine-ness
produced its worst bug: middleware and host-app controllers fighting over `Set-Cookie`. So the server
here is standalone. It has no downstream app, which designs that entire class of problem out.

The engine in this repo runs the other direction. It is the **consumer** half — routes, callback
handling, and session wiring that mount into *your* application, which then talks to the server over
HTTP. Nothing in `engine/` issues a token; it only spends them.

## What it implements

| | |
| --- | --- |
| Authorization code + PKCE | S256 only, and mandatory for public clients |
| Refresh | with rotation — the old token is consumed, a child minted |
| Dynamic client registration | RFC 7591 to create, 7592 to manage |
| Audience-restricted tokens | RFC 8707 `resource` becomes the token's `aud` |
| Discovery and JWKS | per tenant, not per installation |
| Sign-in | password, with an optional TOTP second factor |
| Consent | remembered per actor and client |
| Token exchange | RFC 8693, narrowing scope, audience and lifetime at once |
| Revocation | RFC 7009, cascading to everything exchanged from a token |

## Checked against the spec, not against itself

masks runs the OpenID Foundation's own conformance suite — the plans written against the
specification rather than against what we built. Both certification plans pass:

```
oidcc-config-certification-test-plan    2 modules ·   35 conditions · 0 failures
oidcc-basic-certification-test-plan    39 modules · 2178 conditions · 0 failures
```

It is worth saying what that caught, because none of it was visible to the server's own tests: a
`request` object being ignored rather than refused, `POST /authorize` not being routed at all, a
replayed code leaving its access token alive, and the id token carrying claims that belong at
userinfo. A suite you write yourself only asks the questions you already thought of.

## Multi-tenant from the first migration

masks is the source of truth for tenants, and every tenant has **its own signing keys**. A token
minted for one tenant does not verify against another's JWKS — not as *forbidden*, but as
unintelligible, because the key that signed it was never published where the other tenant could look.

```
$ curl -H "Host: acme.auth.test" -H "Authorization: Bearer $A_JONS_TOKEN" .../userinfo
{"error":"invalid_token","error_description":"Could not find public key for kid e9914114-…"}
```

That is not something you can retrofit onto a singleton key, which is why it is in migration #2
rather than on a roadmap.
