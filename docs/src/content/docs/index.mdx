## Checked against the spec, not against itself

masks runs the OpenID Foundation's own conformance suite — the plans written against the
specification rather than against what we built. Both certification plans pass:

```
oidcc-config-certification-test-plan     2 modules ·   35 conditions · 0 failures
oidcc-basic-certification-test-plan     39 modules · 2178 conditions · 0 failures
```

It is worth saying what that caught, because none of it was visible to the server's own tests: a
`request` object being ignored rather than refused, `POST /authorize` not being routed at all, a
replayed code leaving its access token alive, and the id token carrying claims that belong at
userinfo. A suite you write yourself only asks the questions you already thought of.

## The isolation layer that fails loudly

```
$ curl -H "Host: acme.auth.test" -H "Authorization: Bearer $A_JONS_TOKEN" .../userinfo
{"error":"invalid_token","error_description":"Could not find public key for kid e9914114-…"}
```

Application scopes fail by omission and row-level security fails silently if the connecting role is a
superuser. A per-tenant signing key cannot fail quietly: there is no code path where the wrong tenant
*considers* the token and decides against it.

## Four pieces

```
server/    the standalone OIDC provider     Rails, Postgres, per-tenant keys
client/    masks-client                     discovery, PKCE, exchange, verification
engine/    masks-rails                      the consumer half, mounted in a host app
web/       @masks/client                    BFF and browser PKCE, for an SPA
```
