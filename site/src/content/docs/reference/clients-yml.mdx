_Clients_ are consumers of the masks server. Typically they are web or mobile
apps that manage data only meant for authenticated actors.

For example, you might build a note-taking app that stores encrypted notes. In
masks, you'll want to create a client, give it a name (like "Keep secrets"), and
integrate it with your note-taking app.

## Adding clients

You can add clients in a number of ways:

- As a manager, using the web or API
- Using the Runtime CLI
- With a `clients.yml`

A typical installation seeds a `management` client, allowing managers to add
more clients later on. In most cases, you'll want to ensure additional clients
exist, automatically.

### Command line

Run the following to add a client named _My app_:

```sh
$ masks client:add keep-secrets type=internal
```

You can edit existing clients as well:

```sh
$ masks client:edit keep-secrets allow_sso=false
```

### `clients.yml`

Any clients specified in `clients.yml` will be seeded to the database so that
managers can further customize them.

```yaml
my-app:
  name: My application
  type: internal

admin:
  name: Admins only
  type: internal
  scopes:
    required: admin
```

Refer to the `clients.yml` reference for a full set of options.

## Client types

There are several built-in client types:

| Type                 | Purpose                                                      |
| -------------------- | ------------------------------------------------------------ |
| `management`         | Allows internal access to masks via the web or API           |
| `internal`           | Internal apps hosted on the same domain                      |
| `public`             | Public, PKCE-ready apps (e.g. Mobile, JS, command-line apps) |
| `confidential`       | Backend servers, bots, and other secure apps                 |
| `client-credentials` | Authenticate as a _client_ rather than an actor              |

You can add custom client types if necessary using the `client_types` key in
your `masks.yml`.

<Aside title="An important distinction...">
  _**Internal** clients_ expose tokens via cookies and the session, where other
  types would expose authorization codes, access tokens, or ID tokens (as JWTs)
  in the redirect URL.
</Aside>
