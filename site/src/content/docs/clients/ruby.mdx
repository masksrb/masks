This guide covers integration of _any_ Ruby-based client to a masks server.

<Aside>
  If you want to run a masks server either [self-host a
  container](/guides/self-host) or refer to [the Rails engine
  guide](/guides/rails) to run it inside a Rails app.
</Aside>

## Getting started

Add `masks` to your Gemfile:

```bash
bundle add masks
```

### Rails

If you're building a Rails app, run:

```bash
bin/rails g masks:install
```

Running the `masks:install` generator will add a `config/masks.yml` and update
your routes.

<Aside>
  You must ensure your `config.session_store` is configured properly.
  Cookie-based sessions _**are not**_ recommended.
</Aside>

You can protect controllers and routes:

```ruby
# app/controllers/my_controller.rb
class MyController < ApplicationController
  include Masks::ConfidentialController # For response_type=code clients
  # or include Masks::PublicController    # For public (pkce-enabled) clients
  # or include Masks::InternalController  # Only when used as an engine

  # The index action will require login via the client "my-client",
  # redirecting to /
  mask client: "my-client", only: :index
end
```

### Configuration

You can override configuration via YAML or ENV vars as outlined in the detailed
configuration guide. Just like the containerized deployment, masks will search
for the following files in `Rails.root` for configuration.

| Name                                               | Purpose                       | Path                   |
| -------------------------------------------------- | ----------------------------- | ---------------------- |
| [masks.yml](/reference/masks.yml)                  | General settings and features | `config/masks.yml`     |
| [actors.yml](/reference/actors#actorsyml)          | Default actors                | `config/actors.yml`    |
| [clients.yml](/reference/clients#clientsyml)       | Default clients               | `config/clients.yml`   |
| [providers.yml](/reference/providers#providersyml) | Default providers             | `config/providers.yml` |

You can also customize `Masks` at runtime with an initializer.

#### Dependencies

When used as an engine, you must ensure your app has configured the following
Rails services:

|                |                                                            |
| -------------- | ---------------------------------------------------------- |
| Active Record  | Used to store settings, clients, actors, tokens, etc.      |
| Action Mailer  | Used to send verification emails                           |
| Active Storage | Used to store logos, avatars, and other assets             |
| Active Job     | Used to clean up data                                      |
| `Rails.cache`  | Stores timeouts, FIDO metadata, and other short-lived data |

#### Sessions

You must ensure `config.session_store` is set. _Avoid_ cookie-based sessions.

<Aside type="tip">
  There are a number of downsides to using cookies as the session storage
  mechanism. It is **highly recommended** to use another storage backend, like
  the database, cache, or some other persistent store.
</Aside>

#### Secrets

You must ensure that your app has properly configured and secured the following values:

- `config.secret_key_base`
- `config.active_record.encryption.primary_key`
- `config.active_record.encryption.deterministic_key`
- `config.active_record.encryption.key_derivation_salt`

These are used to secure sessions, hash passwords, and encrypt sensitive data at
rest.

#### Assets & frontend

A hybrid frontend is shipped with masks, allowing a number of deployment
options. The default configurations expects your asset pipeline is properly
set up and precompiled in production.

You can customize the frontend in a variety of ways:

- With basic, per-client theming options
- By including and extending the default UI
- Using the Login API and a SPA framework
- With custom controllers and views

## Usage

The two primary models in masks are:

- Clients (`Masks::Client`) mediate access to resources
- Actors (`Masks::Actor`) authenticate access to resources

The simplest app needs only one client (for itself), plus any number of actors.
A more complex app will have many clients for various use-cases.

### Routing

#### `masks_client(**opts)`

You must add this to your `config/routes.rb` .
add several routes, including:

```
GET /login/:client_id     # only for internal clients
GET /login                # allowed if a default client is configured
GET /token                # for clients that can request tokens
GET /masks                # when management is enabled
GET /sso/:provider        # single sign-on provider callbacks
```

Run `bin/rails routes | grep masks` to see the full list.

##### OAuth/OpenID routes

By default, OpenID/OAuth support is _**disabled**_. When enabled with
`use_masks(oidc: true)` the following routes will be added:

```
GET /login?client_id=...&response_typ...       # Authorization code flow
GET /token                                     # Token endpoint
GET /.well-known/:client_id/...                # Discovery endpoints (JWKS and openid-configuration)
```

Any client with `internal: false` and support for the required response and
grant types (including `type: public`, `type: confidential`, and `type:
client-credentials`) can be used with these routes. Internal clients will not
work.

#### `mask(path, **opts, &block)`

_requires authentication_ for the passed path. A client _must_ be specified:

```ruby
mask "/" # The default client is used, if configured
mask "/staff", with: "my-client", scopes: ["staff"]
mask "/foo", optional: true
mask "/masks", managers_only: true
mask "/api", bearer: true do
  bearer_token.client if bearer_token.scope?("public-api")
end
```

<Aside>
  This works for _any path_, as it checked at the middleware level. Wildcard
  paths are _not_ supported. You can use a similar method in your controllers
  for more fine-grained control.
</Aside>

### Controllers

#### `Masks::InternalController`

When included, adds the `mask` method plus additional helper methods:

```ruby
class WelcomeController < ApplicationController
  include Masks::InternalController

  mask only: :index
  mask only: :staff, scopes: ["staff"]

  rescue_from Masks::LoggedOut do |e|
    # redirect_to e.redirect_uri
  end

  def index
    # current_actor, current_manager, current_client, and current_device
    # are all available in actions and views.
  end

  def staff
    @writable = current_actor.scope?("staff:manage")
  end
end
```

The `mask` method works similar to the method at the routing layer, except it
relies on controller hooks instead of middleware.

### Models

Masks includes the models necessary to function, but your app must specify how
they work. While the YML configuration files and seeds work for simple cases,
you can also interact with the models in code and create dynamic setups.

#### `Masks.installation`

This global mediates access to clients, actors, settings, tokens, and more.

You can change your installation `type` in your `masks.yml`. You can choose
between some built-in types:

- `type: dynamic` loads settings from the database
- `type: readonly` loads settings from `masks.yml`

You can also provide your own _custom_ implementation:

```yaml
# config/masks.yml
type: MyApp::MasksInstallation
```

```ruby
module MyApp
  class MasksInstallation < Masks::Installation::Database
    def client(key)
      MyApp::CustomClient.find_by(key:)
    end
  end
end
```

As long as your installation adheres to the `Masks::Installer` interface most
functionality will work. Take a look at the Ruby API for more information,
including details for `Masks::Actor`, `Masks::Client`, and so on.

#### `Masks::Client`

There are several built-in client types:

- `internal` - Creates internal tokens and redirects
- `confidential` - For backend clients. Returns auth codes, access tokens, and ID tokens
- `public` - For clients unable to keep secrets. PKCE required
- `management` - Only allow masks managers
- `client-credentials` - Create client tokens using the token endpoint

You can also [create your own client types](/reference/masks.yml#clients). For example:

Refer to the [`clients.yml`](/reference/clients#clientsyml) and `Masks::Client` reference for a full list of
attributes you can customize—there are quite a lot!

#### `Masks::Actor`

Actors have:

- identifiers—a nickname, email, passkey, or social login
- credentials—a password, phone number, hardware keys, and more
- scopes indicating access to various resources
- an optional profile, including address, name, etc.

You can seed actors with `Masks.seed`, `actors.yml`, generators, or masks
built-in signup & invitation flows. You can create actors and custom flows in a
number of ways:

- Custom signup & social sign-in
- Invitation, device
- Profiles and account management
- Associations with bespoke records

### Generators

Run the following generators to create/update records from the command-line.
Records that already exist will be updated rather than created.

```
$ bin/rails g masks:actor admin password=password
$ bin/rails g masks:client my-app type=internal
$ bin/rails g masks:provider github client_id=...
```
